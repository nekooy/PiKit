# Custom endpoints, and the two things that hid the failure

*[Architecture](../ARCHITECTURE.md) §6.1.*

## The provider list is pi's, minus what a phone form cannot fill

The picker used to carry ten providers chosen by hand, a set that included neither Kimi nor
Xiaomi. The list is now **pi's own**, from `getApiKeyEnvVars` in the bundled
`pi-ai/providers/all` (the same table pi's help text prints, so it is also the table
`--provider` and the `$VARIABLE` reference in a provider's `apiKey` agree with). Thirty-odd
of them; `PiProviderTest` pins the whole map against a copy of that table, and the sheet
gained a filter field because a list of *things that exist* is a list to search.

Two filters are applied, and both are decisions:

- **OAuth-only providers are out** (`openai-codex`, `github-copilot`): their normal credential
  is an interactive login, which PiKit has no flow for, so a key field would ask for a token
  the user has no way to obtain.
- **Providers that need a second input are out**: `amazon-bedrock` (AWS credentials),
  `azure` (a resource endpoint), `google-vertex` (a project and a location),
  the two Cloudflare providers (an account id, plus a gateway slug for one) and `radius` (a
  gateway URL whose model configuration has to be fetched from it first). Each needs a field
  this page does not have, so the id would look configurable and cannot work. `llama.cpp` is
  absent for the opposite reason — a local server with no credential at all, so there is
  nothing for the key field to hold.

Regional variants stay separate rows, because pi treats them as separate providers with
separate endpoints and model sets (`moonshotai` and `moonshotai-cn`, the four Xiaomi ones,
Qwen's three); where one variable serves two of them — pi reads `MOONSHOT_API_KEY` for both
Moonshot regions — the labels differ and the picker still tells them apart. Anything not in
the list goes through the custom endpoint below.

A relay — an OpenAI-compatible gateway that is not one of pi's built-in providers — has no
`--base-url` flag. The only supported way to add one is a provider entry in
`~/.pi/agent/models.json`, which pi reads at startup and PiKit merges on every launch from the
saved profiles. Getting it to authenticate took two discoveries, both producing the *same*
symptom — `Connection error` followed by three retries, with no mention of the real cause.


## `models.json` is pi's file, so it is merged and never deleted

It used to be rewritten wholesale, and **deleted** whenever the active provider was one of
pi's built-ins, so a hand edit to `models.json` — which pi's own `docs/models.md` invites,
"the file is meant to be edited" — was gone after the next launch. PiKit cannot tell its entry
from the user's, so a writer that owns the whole document will eventually delete something it
did not write. The rules now:

- **The file is never deleted or truncated in place.** Its JSON is merged and atomically
  replaced. An unparseable file is left alone and the launch reports a write failure
  rather than running with a projection it did not write.
- PiKit withdraws its old singleton `pikit-custom` and `pikit-` ids that carry its own
  `$PIKIT_KEY_…` references. An arbitrary user-written id starting with `pikit-` is not a
  reason to remove it. Native entries are not written; only tracked legacy fields are
  withdrawn from those entries (§7.2).
- The file is written only when the encoded document differs, so a launch that changes nothing
  does not touch its timestamp.


## The first write to a `models.json` that does not exist is the one that matters

"Written only when it differs" was `if (target.readText() != encoded)`, and `File.readText()`
throws `FileNotFoundException` on a missing file; the writer's `runCatching { … }.onFailure
{ Log.w(…) }` logged that as `could not merge models.json` and the file was **never created**.
pi then launched with `--provider pikit-custom`, found no such name, and `findInitialModel`
(`core/model-resolver.js`) answered `Unknown provider "pikit-custom". Use --list-models to see
available providers/models.` and called `process.exit(1)`, so the chat page reported
`pi exit with code 1` for a custom endpoint that had been configured. Only the *first* custom
endpoint bites, and `writePiDefaults` had always guarded with `!target.isFile ||`.


## A launch failure had no way back

`selectProfile` committed the new profile and then returned silently when there was no client,
so choosing another provider with the agent dead did nothing; it now relaunches
(`scheduleRestart`). A `Failed` agent disables the composer (`enabled = agent is Running`) and
the failure banner was dismiss-only, so nothing could bring pi back; it now has a **Retry**
button wired to `restartAgent()`, without the 1.5 s debounce kept for settings that change
repeatedly.


## An exit this app caused is not a failure

An intentional stop cancels the exit collector, but cancellation is only observed at a
suspension point: when pi's stdout had already closed as the cancel landed, the collector
returned normally and its tail wrote `pi exited with code 1` over the process replacing it,
so the UI refused to send to a healthy agent. The guard is the client identity: after a
restart the finished flow's source is no longer the attached client.


## A session switch ends the turn that is running, so it is refused

pi has one live session at a time, and `RuntimeHost.teardownCurrent` — the first thing
`switch_session` and `new_session` do — starts with `await this.session.abort()` (verified in
the bundled bundle, not inferred). There is no way to move to another session and leave the
running turn alone, so the app had two options and was taking the wrong one: the command went
through and the answer that was streaming stopped, with nothing on screen to say why.

The app now refuses while `turnInFlight` (`isStreaming` **and** the agent is `Running`; the
second half matters, because a process that died mid-turn leaves `isStreaming` stuck true with
no `agent_settled` coming, and refusing on that alone would lock the user out of their own
conversation list for ever). The refusal comes back as `TurnInFlightException`, so the page
says it in the interface's language rather than the process's, and the text names the way out:
wait, or press Stop and then switch. Deleting the *open* session is refused for the same reason
and at the same moment: it needs a `new_session` to move off the file being deleted, and that
is exactly the command pi will not accept mid-turn.

Two designs were rejected. **Deferring** the switch until the turn settles looks friendlier and
is worse: the tap appears to do nothing for as long as the turn takes, which is
indistinguishable from a dropped tap. **Switching anyway behind a confirmation** ("this will
end the current answer") would be right if the request had been "let me switch and lose the
answer"; it was the opposite, so the default does not kill work a single tap could destroy.
The app's own Stop button is that consent, one control away.


## The key is an endpoint-scoped `$NAME` reference

PiKit exports each key under a route-scoped `PIKIT_KEY_…` variable and gives Pi a
`models.json` reference, `"apiKey": "$PIKIT_KEY_…"`. Pi 1.6.0 resolves that variable,
including when the child switches between same-model profiles without restarting. A keyless
custom route uses a non-secret placeholder because Pi expects a configured credential.

An older release measured `401 无效的令牌` with its previous environment configuration and
succeeded with `--api-key`. That led to carrying the startup key in argv long after `$NAME`
interpolation worked (verified in 1.4.0), at the cost of exposing it through `/proc`. The
app now passes **no** key in argv and writes no aliases to `auth.json`. Pi gives a manual
`auth.json` credential under the **exact** generated alias precedence over the configured
variable; a credential stored under the ordinary `deepseek` or `openai` id is separate.

## An emulator cannot resolve names, so the request cannot leave

The guest's `getaddrinfo` goes through `netd`, so `resolv.conf` is ignored, and the Play-Store
system image is a `user` build, so `/etc/hosts` is not writable. Measured on the guest: TLS to
the relay's address with the correct SNI succeeds and `GET /v1/models` returns 200, while the
same request by name fails with `ENOTFOUND` — the network is fine, only the lookup is missing.
`tools/dns-pin.cjs` supplies that lookup inside the Node process, loaded through `NODE_OPTIONS`
and inert unless `PIKIT_DNS_PINS` is present. PiKit adds the pin to the agent's environment
only when it finds that variable, or a `dns-pins.txt` in its own private directory — neither of
which a user can set, and neither of which a device with working DNS would consult. It is a
test affordance that happens to be shipped, not a feature.


## What the end-to-end run established

With the pin in place, a prompt through the app produced, on the device:

```
user:       run echo PIKIT_E2E_OK and tell me the output
assistant   stopReason=toolUse  tools=[bash]   usage in=833 out=49
toolResult  'PIKIT_E2E_OK\n'
assistant   stopReason=stop     text='The output is:\n\n```\nPIKIT_E2E_OK\n```…'
```

and the chat page rendered it folded: the prompt, a `用时 8s · 2 个步骤` row directly under it,
and the reply.


## A bare host is one path segment short of a working relay

pi's `openai-completions` path posts to `<baseUrl>/chat/completions`, and every example in
pi's own `docs/models.md` carries `/v1`. A user who types `https://relay.example.com` — the
placeholder says `/v1`, and they leave it off anyway — therefore gets three connection
retries per request: severe lag on every prompt, and a chat page that reads as "keeps
disconnecting" for an endpoint that answers `200` on `/v1/models`. `normalizeApiBaseUrl`
appends `/v1` when the URL names a bare host, and leaves a URL that already names a path
alone: `https://gateway.example.com/openai` is a real shape and rewriting it would break
the one endpoint that worked. The same normalisation runs on a *built-in* provider's
override, so the file and the model-list probe agree on the path.

A model list is then asked at both `$base/models` and `$base/v1/models` (and at the parent
of a versioned base), and read out of `{"data":[…]}`, `{"models":[…]}` or a bare array.
Guessing one path and one envelope produced "often cannot fetch a model list" for a relay
that listed them happily under the other key. A rejected key (`401`/`403`) stops the walk
— another path cannot fix the credential — where a `404` is exactly what the next candidate
is for.

### A model-list lookup stays on the configured origin

A gateway can return `401` for the wrong path as well as for a wrong key. Within the
configured origin, the discovery code distinguishes that case from an official endpoint's
credential refusal and may try another known model-list path. DNS and TLS failures end
that walk because another path on the same host cannot change the result.

Falling back to the official provider used to turn one typo into a deceptively valid
model list — and sent the gateway's key to a destination it was not intended for. An
explicit URL is now the only destination for its credential. Its malformed value is
refused, HTTP redirects are not followed, and a native catalogue is used only for a
profile that did not specify an endpoint and whose credential was not rejected.

### A query or fragment is not part of the API root

`$base/models` is how every model-list URL is built, so a base of `https://h/v1?token=…`
became `https://h/v1?token=…/models` — a path the provider never named. `normalizeApiBaseUrl`
rebuilds the URL without query or fragment rather than truncating at `?`, so a base with a
port survives. An endpoint containing userinfo is rejected for routing and discovery.


## A failure the user has to act on is not an English sentence

`ModelDiscovery.Failure` used to carry a string built at the throw site, and the model page
printed it verbatim — so a Chinese or Japanese interface showed `host rejected the request:
HTTP 401`, and the one sentence that said what to *do* about it ("a wrong URL answers 401
just like a wrong key") reached nobody who needed it. `CatalogueProbe.error` had the same
shape and the same problem.

The reasons are now a sealed `DiscoveryProblem` carrying the varying parts (host, status
code, whether the URL was an override) and nothing else; rejected HTTP bodies are not
shown. TLS name, certificate trust, handshake, DNS, timeout and connection failures have
separate tips when the cause is known. The chat reducer gets the same localized diagnostic
with the verified route's host; a provider SDK that reports only `Connection error.`
cannot establish a TLS cause. Neither path weakens certificate verification. The wording is
`Strings.discoveryProblem`'s, in all three catalogs. HTTP codes and host names are not
translated — they are what the reader has to look at. `CliMissing` is its own case rather
than a `PiCannotStart` with prose in the cause, because the fix is reinstalling the runtime
and not retrying.


## The one api name a relay cannot be guessed for

`CustomEndpoint` pinned `api` to `openai-completions` on the argument that "that is what
relays speak" — true of most, wrong for the Anthropic-shaped and Responses-shaped gateways
that have since grown. A wrong name is not a clean error either: pi speaks the wrong
protocol to the endpoint and the stream fails to parse. The field is now on the custom
endpoint's form (`CustomApi`: `openai-completions`, `anthropic-messages`,
`openai-responses`), written through to `models.json`. The picker's labels are pi's own
identifiers rather than translations, because those are the strings in pi's `docs/models.md`
and in the relay's documentation, and the two have to match. A blank field still means
`openai-completions`, so a profile written before the field existed behaves exactly as it
did.


## The protocol decides the version segment, not the URL box

`normalizeApiBaseUrl` completed a bare host with `/v1` for every endpoint, on the argument
that pi's `openai-completions` path posts to `<baseUrl>/chat/completions` and every example
in pi's `docs/models.md` carries `/v1`. That argument is about one client, and the app
offers three. The Anthropic one is `@anthropic-ai/sdk`, constructed with
`baseURL: model.baseUrl` (`pi-ai/dist/api/anthropic-messages.js`, `createClient`), and the
SDK builds its URL as `baseURL + path` where the path is `/v1/messages` (`buildURL`, and
`resources/messages`: `this._client.post('/v1/messages', …)`). A base that already carries
`/v1` is therefore one segment too many. Measured on a phone, with the protocol set to
`anthropic-messages` and a relay's OpenAI base pasted into the field:

```
404 {"error":{"message":"Invalid URL (POST /v1/v1/messages)","type":"packy_invalid_request_error","param":"","code":""}}
```

That reads as a wrong address for an endpoint, a key and a model that are all three
correct, and it names the doubled segment only if the reader knows who appends what. pi's
own catalogue settles the shape: every provider it speaks this protocol to states a base
with no `/v1` — `https://api.anthropic.com`, `https://api.minimax.io/anthropic`, and
OpenRouter's per-model `https://openrouter.ai/api`.

The normalisation is now a function of the protocol:

| `api` | bare host | `…/v1` |
| --- | --- | --- |
| `openai-completions`, `openai-responses` | gains `/v1` | kept |
| `anthropic-messages` | left alone | the segment is removed |

A path that names something else — `https://gateway.example.com/openai`, a gateway's
`…/anthropic` — is left as typed either way: that is where the gateway lives, and only the
version segment is the client's business. The custom definition uses its configured API;
`ProfileRoutes` uses each built-in model's bundled (or origin-checked cached) API to normalize
that model's relay URL. A bare host guess cannot select between an OpenRouter Anthropic model
and an OpenAI model. Discovery uses the protocol to choose `/v1/models` and `x-api-key` plus
`anthropic-version`, versus `/models` and Bearer auth; the other same-origin path can be tried.
`NormalizeApiBaseUrlTest`, `ModelListShapeTest` and `ProfileRoutesTest` pin those boundaries.

## A projection that could not be written must not be used

A writer used to skip the first file for a native override without any `models` entries.
Pi then started with Xiaomi's official endpoint and returned `401` for a relay key. It also
used to keep one built-in profile under Pi's native id: clearing one override or reordering
profiles could make an official model request remember the relay's address instead.

An override still keeps the provider's catalogue and API, but it changes only that profile's
alias. All aliases, including official profiles, have explicit model definitions. The writer
withdraws only recorded old fields from a native entry (`writtenBaseUrl`, `writtenModels`),
including old spellings of the recorded URL; unrelated native settings remain untouched. A
write failure or a missing route is an error before a model request, never an excuse to try
Pi's native provider id.


## The check that says "filled in" and the check that says "usable" have to be the same one

`normalizeApiBaseUrl` refuses anything that is not an absolute `http(s)` URL with a host,
and answers `""` for `localhost:11434` — which has a scheme-looking colon and no host. The
form's refusal, though, asked `baseUrl.isBlank()`, and `isConfigured` asked the same. So a
URL the writer would drop could be saved, and a custom endpoint saved that way reached pi
with no `pikit-custom` entry in `models.json` and died with `Unknown provider "pikit-custom"`
followed by `pi exit with code 1` — an error that names neither the field nor the missing
scheme. "Fetch models" said "Enter the endpoint's base URL first" for a field the user had
filled in.

All three now ask the normalised value: `refusal()` refuses a non-blank field that
normalises to nothing (`invalidBaseUrl`, in the catalogs), `isConfigured` requires
`normalizeApiBaseUrl(baseUrl).isNotEmpty()` for a custom endpoint, and `discover()`'s
message for a filled-but-unusable field says what shape a URL has to be.


## Per-model settings are the form's, not the previous visit's

The save used to write `existing.modelSettings` whenever `catalogueIds` was null, on the
argument that a check which could not run must not delete what the user chose. A custom
endpoint never runs that check, so the three numbers and the image switch the user had just
set were dropped on every save and the reopened form showed empty rows. The form's own map
*starts* as `existing.modelSettings` and only the controls move it, so filtering that map by
the ids still listed is both the new edits and the old carry-over — one rule, and the one
the report was about.


## What a second pass found that the report did not name

The first pass fixed the four symptoms that were reported. Walking the same chain end to
end again turned up five more defects that produce the *same* three feelings — lost
settings, a dead or flaky agent, a request that never arrives — from a screen that looks
like it saved:

- **A provider switch kept the endpoint field.** It used to be inert for a built-in
  provider; once it became an override, a relay URL typed for `pikit-custom` and left on
  the form after a switch to DeepSeek rewrote every DeepSeek model to that relay. The
  field and its withdrawal record are cleared with the model list now, and the record is
  never carried across a provider change.
- **Every save of the active profile restarted the agent**, including a rename — which
  `stopAgent` turned into a killed turn that read as a disconnect. A restart is now
  scheduled only when a field the *launch* reads has moved, and a deferred restart waits
  for `turnInFlight` to clear instead of tearing the process down mid-answer. Choosing a
  model belongs to the composer's chip, so the settings list no longer has a
  tap-to-activate of its own either.
- **A catalogue refresh emptied every definition.** The old basis gate withdrew native
  definitions until the model page was revisited, resetting the user's numbers. The
  isolated entry now merges the user's settings onto the current model facts at launch;
  refresh itself never replaces a running child's configuration.
- **A non-URL was completed and written.** `localhost:11434` has a scheme-looking colon
  and no host; it was turned into `localhost:11434/v1` and registered as a provider that
  cannot be reached. `normalizeApiBaseUrl` now refuses anything that is not an absolute
  `http(s)` URL with a host.
- **A config write that failed looked like a save.** `ProfileStore.upsert` dropped
  `PiConfigFile.save`'s answer, so a full disk was a successful form until the next launch
  re-read the old file. The failure is surfaced as `saveFailed` now.

A failed profile write is not published. A built-in profile requires a key; a custom
endpoint requires a valid URL and can be keyless.
