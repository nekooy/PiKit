# 9.3. The web-access and maintenance pages

*[Architecture](../ARCHITECTURE.md) §9.3.*

Two settings pages that needed an argument of their own: the bundled
`pi-web-access` extension and the options PiKit is willing to own of it, and the runs
behind `Settings → Maintenance & repair`. The furniture both are built from —
the app bar, the card, the row, the note — is §9.2's.

## The web-access page owns six controls, and documents the rest itself

`pi-web-access` 0.46.0 — the version the runtime image vendors — reads around 150
configuration keys. The page used to present a *selection* of them: a master switch, two
pickers, three toggles, four numbers and seven credential fields, laid out as if that were
the configuration. Two things were wrong with that: the provider picker listed eleven
services where the extension resolves **forty-three**, so a Kagi or Serper user concluded their
provider was unsupported (`WebSearchSettings.SEARCH_PROVIDERS` is now the extension's own
list, and `WebSearchStoreTest` pins the count); and a *drawn* control is also a writer —
`githubClone.enabled` defaults to `true`, so a switch the page showed as on, because it had
never seen the key, would silently re-enable cloning over a file that had turned it off. The
line is therefore not "the important options" but **"the keys PiKit is willing to own"** —
six controls, standing over ten keys: the master switch's five, the workflow, the provider,
the inline-content limit, the fetch timeout and the proxy. The rest of the configuration is
a **list plus one button**, and the file's own syntax is not something the user has to know.

**The master switch is five keys, and for one revision it was nine.** The extension has no
switch of its own: `webSearch.enabled` is an older shorthand that unregisters two of the
four tools, so the switch writes all five — the shorthand plus the four
`tools.<name>.enabled` — and reads them the way the extension resolves them
(`isToolEnabled`), which makes it off only when the extension has no tool left. What it does
not cover is the extension's four commands: `/websearch`, `/curator`, `/search` and
`/google-account` sit behind `commands.<name>.enabled`, **default to on**, and `/websearch`
reaches the same search stack the tools do — so with the row reading "off", a command typed
into the composer can still search the web. Widening the switch to those four keys was
written and tested — nine keys, read through `isCommandEnabled`, with the aggregate rule
"off only when the extension would register nothing at all" — and then withdrawn, for the
reason the five-key switch already shows in miniature: **every key the switch owns is
rewritten from its one boolean on every render**, so a hand-edited
`commands.search.enabled: false` is overwritten by the next tap anywhere on the page. Nine
keys doubles that surface — and the keys a reader is most likely to have set by hand are the
ones the extension documents — for a gap narrower than it looks, since a command is a
deliberate act and PiKit already defaults `workflow` away from the curator that `/websearch`
opens. `WebSearchStoreTest` pins the decision instead: the commands stay the file's, are not
in `WEB_SEARCH_OWNED_PATHS`, and survive a render untouched. **The other design rejected on
the way is unregistering the extension instead** — removing its absolute path from pi's
`packages` — which would close the command gap by a shorter route, at three costs: that file
is pi's and this app only ever appends to it, so a toggle would be the first write that
removes one of the user's own entries and would have to decide which entry is "ours" when
they added the path in another spelling; a `packages` key that is not an array is a state the
app already handles by declining to write, where the switch would silently stop working
instead of staying honest; and the only thing it buys over the config keys is not loading
0.98 MB of JavaScript at pi's startup.

**What used to be here, and why it went.** The section was a text editor holding the whole
rendered document — PiKit's six keys uncommented with the values in effect, every other key
as a comment carrying its path and a usable example — and it asked the user to write JSON to
set one API key, on a phone keyboard, in a box about 46 columns wide, where the one thing
that mattered (which of three hundred lines are live) had to be read off a marker in front of
a `//`. The renderer, the schema list and the comment reader all remain, because
they are what keeps the *file* correct and what the fallback editor still shows.

**The list is the file.** `WebSearchStore.extra` walks the document and reports every live
key the page's controls do not own: a documented option whole — `curatorRemote` is one row,
not one per member — and an unknown key by its leaf path, which is the only name it has. The
order is the file's own. Removing a row removes that path and prunes any object the removal
emptied, because the extension reads a present-but-empty branch as configured, and the page
would otherwise list `fetch` for ever after its last member was removed. A key the controls
own is never listed and can never be set from here — the renderer writes those from
`WebSearchSettings` on every render, so a value added there would be overwritten by the next
tap anywhere on the page. `WEB_SEARCH_OWNED_PATHS` is the one list both sides read, and
`WebSearchStoreTest` pins it against the renderer's own live keys.

**One button adds one option.** It opens `WEB_ACCESS_PARAMS` in the app's picker — with a
filter field, because a hundred and forty-eight rows is past the point where scrolling is
finding. The sheet that follows takes the value, and its shape follows the option's type: a
`string` option is stored as a JSON string, which is what makes `$XAI_API_KEY` work and what
keeps `"sk-…"` with its quotes from being the tax this section exists to remove. Everything
else is parsed as JSON, so a `boolean | object` option accepts either shape and a `"50"`
where a number belongs is refused rather than quietly stored — the extension ignores a value
of the wrong type, and a field that says why is worth more than a setting that does nothing.

**The file on disk is not the document, and the difference is a bug that shipped.** The
extension parses `web-search.json` with a bare `JSON.parse` — `loadConfiguredProxy` in its
`utils.ts` and a `loadConfig` in every provider that takes a key — so a single `//` in the
file fails *every* web tool with `Unexpected token '/' … is not valid JSON`, and
`web_search`, `fetch_content` and `source_check` were all dead on a default install. The two
are separated now: the **document** is what the renderer produces and what the fallback
editor shows, comments and all, and the **file** is `strictDocument(document)` — the same
text parsed with the comment-tolerant reader and re-encoded as plain JSON, so only the keys
that are live are in it, and no comment ever is. `ensureDocument` repairs an install that
predates the fix: a file that is a JSON object once comments are stripped but not as it
stands is rewritten in the strict form at the next launch — one that is already strict keeps
its bytes, including a hand-written one whose formatting differs from PiKit's, unless it is
missing a default PiKit writes (below) — and one that does not parse at all is left for the
editor, which is the only way out of it.

Four details make the renderer work, and each is pinned by a test:

- **Comments are read on the way in, never written.** `stripJsonComments` — pi's own two
  regular expressions from `utils/json.js`, no block comments — reads them, so the document
  may contain `//` comments and trailing commas. It is a *reader* only: a file with comments
  in it is a file no tool can use, so the writer's guard is `strictDocument`.
- **A write may not lose anything.** Rendering walks the schema tree, so a key the document
  already has is written uncommented with its value, and a key the schema has never heard of
  is written uncommented where it was found, with a comment saying it is not PiKit's. The
  user's own formatting is the one thing not preserved, which is the point.
- **Some objects may not be empty.** `searchRouting.providers` and
  `fetchRouting.providers` are required once their parent exists, so an `{}` there is a file
  the agent refuses to start on; those two branches are written as a commented block until
  the user gives them a value. Every other branch may be an empty object, which the extension
  reads exactly as an absent key.
- **The document has no trailing commas, and that was measured.** On the real rendered
  document, handed to the extension's own `stripJsonComments` and then to `JSON.parse`,
  **two survived and the parse threw** — the string-literal alternative in its second regular
  expression can swallow a comma followed by comment-stripped blank lines, depending on where
  the scan happens to be. So the document is valid JSON with nothing in it that needs
  stripping, and the editor's Save says so instead of writing a document nothing can parse. A
  test asserts the property directly, because it is invisible in review and fatal on the
  device.

The document draws **a blank line between every two siblings**, at every depth, which costs
nothing in the file: a blank line is dropped by `strictDocument` along with the comments, and
an empty line inside a commented block stays empty rather than becoming a bare `// ` (which is
what `commentedOut` had to be taught).

The rows document the extension as it is, not as its README describes it: the project's `main`
branch documents `serplyApiKey`, `fetch.defaultMode` and `webSearch.allowedProviders`, none of
which exist in any published release. The examples use `$NAME` references rather than
placeholder keys, because the extension treats an unset variable as *not configured* — so a
value filled from the example cannot turn a working search into a broken one, which `"sk-..."`
would.

"Restore defaults" is the one destructive control on the page and it asks first: it puts the
fresh-install configuration back, which takes every key the user typed with it.

**A default PiKit writes: the range a fake-IP proxy answers with.** `fetch_content` was
refused on a phone behind a Clash-style TUN proxy, and so were the pages `source_check`
fetches and the pages `web_search` pulls in when it is asked for content. The guard is the
extension's `assertPublicAddress` (`ssrf-protection.ts`), and it runs on the address a URL
*resolves to*, before anything is connected — so the TUN device that would have carried the
request never saw it. Such a proxy answers every public hostname with an address in
`198.18.0.0/15`, the synthetic range the preflight refuses, and `loadSsrfConfig`'s default
for `ssrf.allowRanges` is the empty array, so a default install refuses it. The extension's
own message names the fix — `… commonly used by TUN/fake-IP proxies. If that matches your
setup, configure ssrf.allowRanges with ["198.18.0.0/15"]` — and PiKit now writes that value.

**It is a default, not one of the controls' keys.** An owned key is rewritten from
`WebSearchSettings` on every render, which is what made the nine-key master switch a bad
idea above, and this value is a security policy the user may have made by hand: `[]` is the
extension's own meaning for "exempt nothing", and a list of LAN ranges is their own network.
A switch that rewrote either on the next tap would be that bug again. So the key is written
only when it is *absent*: `WEB_SEARCH_DEFAULT_KEYS` in `WebSearchStore` holds the one entry
PiKit writes into a file that does not have it, and nothing in `WEB_SEARCH_OWNED_PATHS`
changed.

**Two entry points, because a fresh install and an existing one are different questions.**
The document a fresh install gets — `WebSearchStore.defaultDocument`, which is also what
"Restore defaults" puts back — is rendered from `WEB_SEARCH_DEFAULT_SOURCE`, a source that
already holds the default, so the schema places the key in its documented position, the
editor shows it live with the note `WEB_ACCESS_PARAMS` gives it, and the strict file has it
because the document does. An existing install's file is already strict and keeps its
bytes, so a render would never add the key to it: `mergedDocumentText` merges the missing
default in, reached through `ensureDocument` — the launch-time step the strict conversion
already uses — and therefore also through `reload`, which now repairs before it reads
rather than after, so the page's list is the file the agent will see. That merge is the one
write in this class nobody asked for with a tap, and it is an *addition*: every key in the
file keeps its value and its type, a file PiKit wrote keeps every other line byte for byte,
and a file formatted by hand comes back in PiKit's shape — the shape the first control tap
would already have given it — because a byte-level insert is a JSON position parser in the
one part of this app whose history already contains a hand-rolled JSON reader. A file that
is strict *and* already has the key is written by neither, which is why the merge can run at
every launch.

**`ssrf.trustEnvProxy` was the other candidate and it is the wrong one here.** It does not
exempt an address; it skips the DNS preflight when the extension has a proxy of its own to
trust — `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` in the environment, or the file's `proxy` key
when it is one of the remote-DNS schemes and the host is not in `NO_PROXY` — and then it is
that proxy, not the TUN device, that resolves the name. PiKit sets no proxy environment, and
a TUN proxy is not an environment proxy at all: on a default install the key would change
nothing and the address would still be refused, and on a configured one it would hand the
resolution to a proxy the user may not have. Exempting the range says what is true of the
setup; trusting a proxy nobody configured does not.

**The row is the file's, and what removal costs is stated rather than hidden.** The key is a
live key no control owns, so it appears in the list and the row's remove control takes it
away, and "Restore defaults" puts it back. What that control cannot do is make the absence
stick: it deletes the key, and the next launch's merge writes it again, because the file is
the only record and an absent key cannot be told from one that was never there. `[]` is the
refusal that does stick, and it is exactly what the extension means by it.

## The maintenance page says when to press it, and its runs are one shape

The page states two facts — the pi version inside the runtime, and what the package ledger
holds — and its rows carry the controls that start six runs: the model list's refresh,
the relocation walk, the environment rebuild, the storage check, and the two package runs
the ledger adds only when it has something to report. None of them is housekeeping: a row
that reads as routine work is a button pressed on a healthy install. There is
deliberately nothing here that updates pi itself — it is an input of the runtime image,
so it moves only with a PiKit release (§2, §3).

- **The installed version.** `Installed version` reads pi's own `package.json` out of
  `$PREFIX` and sits above the model list, because the two facts are the bundle and its
  metadata. A version of a thing is read on the row that owns it (§9.2).
- **The model list.** The row is "Model list / Updates the model list on demand", the button
  is "Refresh", and the run announces itself as one toast ("Contacting the providers…") and
  answers with another ("Updated" or "Latest"). The page prints no note about the four-hour
  automatic window or the network it needs: the window is §7.2's subject, and a paragraph
  explaining a button is read as a reason to press it. The run's state is `CatalogueUpdater`,
  held by `SettingsScreen` rather than by the page, so leaving mid-refresh does not throw the
  result away; the button and the launch path go through one function
  (`PiAgentSession.requestCatalogueRefresh`) so they cannot come to mean two different things
  about the store on disk (§7.2).
- **The package ledger.** `Packages` is a fact rather than an action, read when the page
  opens: what the reader installed with `pkg install` survived the last runtime update, what
  is still waiting to be restored, and what the bundled environment ships a newer version of.
  The value is the ledger's own count. The two runs below it exist only while that count has
  something to say — an update row for the packages the image ships ahead of, a restore row
  for the ones a restore left behind — so the section has no button for a gap that is not
  there. The page used to answer both states with a note naming `pkg upgrade` /
  `pkg install -y`, and the note's own limits are what made that the wrong shape: it named a
  command the reader had to retype into another page, it could not report what came back,
  and the sentence was a paragraph to scroll past on every visit, including the visits with
  nothing to do. **The work is the installer's, not the terminal's**, because a package is
  only installable through the prefix hooks — apt's `DPkg::Pre-Install-Pkgs` relocation plus
  the `dpkg` wrapper around `dpkg.real` — and a session that shelled out to the terminal page
  would be the same command with a screen attached to it, still downloading after the reader
  left that screen (§4). Both runs are `BootstrapInstaller`'s, launched on the session's
  scope so they survive the page leaving the composition, and each is guarded by a
  compare-and-set on its own running flag: two taps in one frame would start two apt runs over
  one database, and the second would wait on the lock the first holds, which is
  indistinguishable from a hang (§13).
- **A package run needs a network, and says so.** The count the ledger shows is a comparison
  against the bundled `build-metadata.json` and needs nothing but the device; the run that
  closes it downloads archives from the package index, so the row's subtitle is the only place
  the cost is stated — a button read as offline maintenance is a button pressed on a plane. The
  update is bounded at 15 minutes, where the restore's two passes are bounded at two minutes
  each: a copy out of apt's cache is local, while an upgrade is a download whose bound exists so
  a mirror that stopped answering cannot leave the row spinning for the life of the process. A
  run that fails reports twice over — the sentence is what the ledger's re-read could establish
  (how many are still behind) and the bounded tail of the log is where it stopped — and a run
  that throws, times out or is killed says the same thing in the same dialog, because that is
  the same reader looking at the same block.
- **What the ledger says afterwards is the run's answer.** A success is a toast and nothing
  else; dpkg's status is re-read when the run ends, whether it exited zero or not, because
  `pkg upgrade` updating most of the list and failing on one package is a real outcome. So a
  successful run with packages still behind the image re-draws the update row with a smaller
  count rather than declaring the environment current, a restore that brought everything back
  removes its row and the manifest with it, and a failed run's dialog is dismissed into a ledger
  that already reflects what did happen. That is why the page reports the ledger instead of the
  run's exit status: the exit status is the operation's, the ledger is the environment's, and
  the environment is what the reader came for.
- **The relocation row is for a tree that already fails.** Anything installed with `pkg` or
  `apt` is rewritten as it installs, so `Repair` is for a package that arrived another way
  and refuses to start. That framing is the rule even though the long sentence it used to
  sit in is no longer printed: a repair button read as routine maintenance is a button
  pressed on a healthy install (§4).
- **The rebuild is the escape hatch, and it asks first.** `Rebuild the environment` unpacks
  the runtime again; the packages the reader installed are recorded first and put back
  afterwards, which is what the confirmation says, including that anything apt no longer
  holds a cached archive for needs a network. It is the row a repair points at when the
  relocator itself is damaged, because a repair cannot fix that state (§4), and its outcome
  is not a toast or a dialog here: it replaces the runtime, so the setup screen the install
  path already draws is where it reports.

**The runs are one row each, and the three ways the earlier ones differed are the argument.**
Each run draws one `BasicComponent` whose trailing slot holds its one control — the button, or the
live spinner while it is going — and whose title and subtitle never move. What was there
before was three call sites written out by hand: the state of the *storage* run was in the
row and the other two said it only in a paragraph; the two tree walks drew a progress bar
and the self-test drew none, so a run in flight and a run that never started looked the
same; and every button sat at a 12dp gutter while the note under it sat at 16dp — measured
at the time of the fix, the label of `立即刷新` at x=127 inside a pill whose left edge was
x=64, against its own note's text at x=74, a 4dp step that reads as a mistake rather than
as a decision. The row's value column then carried each run's state and its tone, until it
was measured squeezing the words beside it: mid-walk, `正在检测…已扫描 2816 个文件` held
464px of the row while the title was left 182px wide and wrapped across two lines. The
state left the row for the app's toast (§13), which is where a finished moment belongs
anyway; the reader's report still describes the control
(`把那些操作按钮放到列表右边…点击后显示那种转圈的团状ui，然后显示已是最新` — the
button, the spinner, then the result; only the result's address moved). A shared strip
was an earlier fix and is still the *backup* page's shape, where a run has a sheet of its
own to stand in.

**A success is a toast; a failure is a dialog.** The completion banners are gone: the
catalogue's `已更新`/`已是最新`, the relocation's `已修复`/`无需修复` and the self-test's
`通过` arrive as toasts — a moment, gone after a few seconds — and a banner repeating one of them
in a sentence was one of the "完成的横幅" the page was asked to drop. A *failure* is an
operation that came back wrong, and in settings that is announced and then dismissed: a
dialog carrying the failure's sentence in the error-tone frame, the walk's unrewritten
files or the script's failing lines bounded and scrolling below it, and one OK — which is
also the run's own clear call (`catalogue.dismiss()`, `selfTest.dismiss()`,
`clearRepairResult()`), so reading the failure and dismissing it are one press.

**The button comes back when the spinner goes.** A run's control is the row's whole
furniture: there is no verdict in the row and no hidden button to bring back. The shape
this replaced hid the button once a verdict arrived and made the row itself the dismiss;
that is what kept the three clear calls reachable, and with the verdict gone from the row
they moved to the dialog's OK. The catalogue's `refreshVersion()` still runs at the run's
*end* (a `LaunchedEffect` on the status) — the moment the page is about to be looked at
again — reached without a button.

**The self-test's run is deliberately still one bar and no fraction.** The walk reports how
many files it has read (`repairScanning`) and the catalogue refresh has nothing to report at
all; the self-test has no number between "started" and "finished" either, and inventing one
would be a bar that lies.
