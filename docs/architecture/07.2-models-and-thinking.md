# The model and thinking-level switches

*[Architecture](../ARCHITECTURE.md) §7.2.*

## One provider, many models

A saved profile is a **provider** — an endpoint and a key — and it carries a list
of models. It used to carry exactly one: trying a second model meant creating a
second profile and pasting the same key again, and the fetch-models picker could
only ever *replace* the single model, so the first one disappeared the moment a
second was chosen. The field is `ModelProfile.models`, with `modelId` kept as the
model in use — the field the launcher and pi's own `set_model` already speak in —
and a profile written before the list existed reads back as
`selectableModels == listOf(modelId)`, so nothing has to be migrated.

The picker follows: each entry is a model of a profile, with the provider as the line
under the model id, so the chip and the menu answer "which model", not "which
profile". The chip shows the profile's own choice and falls back to the model pi
reports — a profile's *name* stops identifying anything once one provider holds four
models. The picker is a floating menu at the chip (`PiMenuRow`, the anchored half of
the modal layer — §7.1), which is what the level picker under it is too; the row's
second line is where the provider and the profile name went once the panel stopped
being a sheet with room for group headings.

**The store had to become state.** `ProfileStore` kept its document in a plain
field, so the UI read a snapshot with nothing to tell it the snapshot had changed.
That produced two bugs: the composer's model chip kept showing the model it had been
composed with, and the picker's tick — whose values were captured in the click
handler's closure — went on ticking the model from the *previous* composition, so
the chip and the tick could point at different rows at once (caught on the emulator:
chip `mimo-v2-extra`, tick on `mimo-v2.5`). The store now publishes a
`StateFlow<PiConfigSnapshot>`; the chip, the picker, the model page and the settings
root collect it, and the picker reads its list *inside* the menu rather than through
the lambda that opened it. A body that must show current data has to read the source,
never a captured value.

**`models.json` has to list them all.** For a custom endpoint PiKit writes pi's
catalog entry, and pi answers `set_model` from the catalog it built at startup. A
provider registered with one model can therefore only be switched *away* from by
restarting the agent for a change pi would otherwise apply over RPC. Measured before
the fix: picking the second model of one custom endpoint logged
`launching: … --model mimo-v2.5`, where picking the first had been applied in
place. After it, both switches happen with no `launching:` line at all.

## Every saved profile is loaded at launch, and "profile" is a provider id

A saved profile is a provider-and-key pair, and pi keys **both** by provider id — one
credential and one `baseUrl` per id, in `models.json` and in the environment. Two saved
profiles of one provider therefore cannot both be called `deepseek`, and the single
shared `pikit-custom` id this app wrote until now could only ever be one relay. What a
profile is called is `ProfileAddressing.runtimeProviderId`, and it is one answer used in
four places that used to agree by hand: the id `--provider` names, the id `set_model` is
told, the id the `models.json` entry is written under, and the `defaultProvider` a
hand-run `pi` reads out of `settings.json`.

- the **first** profile of a built-in provider keeps pi's own id, which is what gives it
  pi's catalogue, its `compat` table and its default endpoint;
- a **second** profile of the same provider is `pikit-<profile id>`, with the host, the
  protocol and every catalogue field of every model copied in — `compat` included, since
  that is where DeepSeek's reasoning format lives;
- a **custom endpoint** is `pikit-custom-<profile id>`.

Every profile's key then goes into the launch environment under `PIKIT_KEY_<profile id>`
(plus the provider's own documented variable for whichever profile owns pi's id), and its
entry names that variable as `apiKey: "$PIKIT_KEY_…"`. pi decides which providers are
usable from credentials alone, so a launch carrying all of them has all of them — and a
`set_model` across profiles succeeds in the running process. Measured against the pinned
pi 1.4.0: a document with a `deepseek` entry, a second profile `pikit-b` built from
`models-store.json` and a relay `pikit-custom-r` lists all three with the catalogue's own
numbers, and two `set_model` calls move the running agent across both without a restart.

The env is the whole of the *sharing*: the terminal tab's login shell is handed the same
map and the same session directory, so a `pi` typed there finds the same providers, the
same credentials and the same conversations. `--api-key` is still passed for the launched
profile (pi's first-precedence credential), but it is no longer the only thing that
authenticates a relay — see §6.1.

**An id nothing defines cannot be launched, so it is not named.** Measured on a device:
a second DeepSeek profile whose entry had not been written was launched as
`--provider pikit-ba076308`, and pi answered

```
Error: Unknown provider "pikit-ba076308". Use --list-models to see available providers/models.
Error: --api-key requires a model to be specified via --model, --provider/--model, or --models
```

and exited 1 — a chat page that cannot start, and Retry repeats it. The second line is the
first one's consequence, not a missing `--model`: the same pair reproduces with a model
named. So `ProfileAddressing.launchProviderId` names a profile's own id only when the file
defines it, and falls back to pi's own provider id for that provider otherwise: the app
runs on the profile's key (`--api-key`), and switching to that profile costs the relaunch
it used to. `set_model` must not take that road, because with the profile unregistered pi
would answer from the id that *is* registered — the other profile's credential.

**And the refresh has to carry the same variables.** pi resolves a provider's credential
while refreshing, and **one** unresolvable `apiKey` aborts the whole run:
`Could not refresh model catalogs: deepseek: Failed to resolve API key for provider
"deepseek" from environment variable: PIKIT_KEY_a`. That is how the device above lost the
catalogue facts its entry was built from, so the two failures fed each other: the refresh
carries every profile's key now (`catalogueRefreshEnvironment() + providerEnvironment(…)`),
and an entry is never written for a profile with a blank key — a `$NAME` nothing exports
is worse than no entry, because it takes every other provider's refresh down with it.

**And a profile that needs the catalogue asks for the refresh by need.** A duplicate
profile's entry cannot exist until the store describes its provider, and the refresh that
would fill the store sits inside a retry window whose deadline a *failed* attempt wrote —
which is precisely the state a device whose refreshes had been failing is in. So
`needsCatalogueFacts` runs the refresh regardless of the clock when a saved profile's
models are absent from the store: the cost of being wrong is one background attempt per
launch on a phone with no network, and the cost of waiting is a profile that cannot be
switched to without a relaunch for half an hour. The refresh's own change detection then
relaunches the agent, and that launch is the one that registers the id.

**It asks for a provider's first profile too, and that reason is the levels.** A provider
whose catalogue is not inside pi's package has no facts to fall back on: measured against
the pinned 1.4.0 with an empty store, `xiaomi/mimo-v2.6-pro` resolves through
`buildFallbackModel` and `get_available_thinking_levels` answers `["off"]`; with pi.dev's
catalogue on disk the same call answers `["off","high"]` and the model reports
`contextWindow: 1048576, reasoning: true`. So on a phone whose store is empty, every level
the reader picks while on that model comes back as `off` — which reads as "the thinking
level follows some other model", and is a missing catalogue rather than a wrong level. An
owner profile writes no entry, so nothing else in the launch path would ever have asked
for that refresh.

**The store has two readers, and they answer different questions.** `storeModelFacts` is
the *model* half of an entry — `api` and `baseUrl` stripped, because a relay that fronts
`claude-sonnet-4-5` inherits the window, the price and the thinking map of the id and must
keep its own endpoint. `storeProviderModels` is the same models **as pi wrote them**, host
fields included, and that is the only source for the provider-level `api`/`baseUrl` of a
second provider id: `builtInProviderObject` refuses to invent a host
(`if (baseUrl.isEmpty() || api.isEmpty()) return null`), so an entry built from the
stripped map was silently never written — and the profile it describes restarted on
**every** pick while the first profile of that provider switched in place. `deepseek` is
the case that shows how well that failure hides: pi's bundled catalogue has the model, the
store has the provider, and the only thing missing was the two fields a helper had taken
out for a different caller.

## The thinking levels offered are the model's, and pi's answer is what is saved

pi's seven levels are not a menu every model honours.
`getSupportedThinkingLevels` (`pi-ai/dist/models.js`) filters them through the
model's own `thinkingLevelMap`, and `set_thinking_level` **clamps** a request the
model cannot satisfy by walking *forwards* to the next level it can. DeepSeek's
catalog says `{minimal: null, low: "low", medium: null, high: "high", max: "max"}`
for `deepseek-flash`, so the model has four levels, and asking it for `medium`
leaves pi on `high`.

Two bugs came out of ignoring that: the picker offered all seven, so tapping
`medium` left `high` on the chip — the level pi had actually set; and the saved
level was never brought up to date, so the saved `medium` was passed as `--thinking`
again on every start, the chip showed it, and `get_state` then moved the chip to
`high`. Once per launch, forever.

So the app asks pi for the model's levels (`get_available_thinking_levels`, folded
into `ConversationState.availableThinkingLevels` whenever a state refresh happens)
and offers exactly those. `clampThinkingLevel` mirrors pi's rule on the JVM for the
one case pi has not answered yet, and `ThinkingLevelTest` pins it against the maps in
the shipped catalog.

## The picker is right on the frame the model changes

A model switch causes **two** replies — `get_state` naming the new model, then
`get_available_thinking_levels` — and between them the previous model's list was
published as the current model's menu. The list had no key at all
(`ConversationState.availableThinkingLevels` was a bare `List<String>`), so the picker
offered whatever the last answer of the run had been: pi's seven levels over a model
that has three, or `deepseek-v4-pro`'s menu while `deepseek-flash` was being selected.
It is the same class of bug the *remembered* levels were introduced for and it survived
that fix, because the memory was keyed and the live list was not.

Two changes close it, and they answer different halves of the window:

- **The live list is keyed, and cleared when the model moves.**
  `ConversationState.availableThinkingLevelsFor` records the model pi's answer was
  about, the reducer sets it from `state.model` on the reply, and `get_state` naming a
  different model drops both the list and its key. `thinkingLevelsFor` then treats a
  live list whose key is not the model in use as no answer at all.
- **The catalogue on disk answers for the model that is not running yet.**
  `models-store.json` already carries every catalogued model's `thinkingLevelMap` — it
  is the file the launch path refreshes for every built-in provider (§7.2, above) — so
  `readCatalogueThinkingLevels` turns it into `model id → levels` with
  `supportedThinkingLevels`, a JVM copy of pi's own `getSupportedThinkingLevels`
  (`off, minimal, low, medium, high, xhigh, max` filtered through the map: a level
  mapped to `null` is refused, `xhigh` and `max` exist only when the map names them, and
  a model with `reasoning: false` has exactly `["off"]`). The session reads it on the
  launch path and after every catalogue refresh, and publishes it as a `StateFlow`.

The precedence is `thinkingLevelsFor`'s: pi's live answer **for this model**, then the
list remembered for it, then the catalogue, then pi's seven. Both caches are keyed,
which is the whole point — an unkeyed list is a wrong menu, not a missing one. The level
the chip *shows* is clamped against the same list, so a preference the new model cannot
honour reads as what pi will clamp it to rather than jumping a second later.

A catalogue entry that says neither `reasoning` nor `thinkingLevelMap` is left out of
the map rather than read as "no reasoning": silence is not an answer, and the fallback
to pi's seven is a better menu than one row invented here.

**The *model* the question is about is decided before pi answers, too.** The levels
above answer instantly once the *model id* is right, but the id itself had the same
round-trip lag: `modelInUse` trusted pi's live report, and on the frame the user picked
a model the live report still named the previous one — for as long as the confirming
`get_state` took, measured at 320 ms on the emulator and over a second on a busy phone.
`ConversationState.requestedModel` is written by `selectProfile` (and by
`scheduleRestart`, whose 1.5 s debounce plus spawn and handshake is a longer window
over the same gap) on the frame the switch is made — the profile store is committed
synchronously — and `modelInUse` reads it first. `get_state` settles it: naming the
requested model leaves it standing, naming anything else (a `/model` typed into the
composer, a restart that raced the switch) drops it, because what pi is running is the
answer. The settings page's own switch is covered by the same write: it only restarts
the agent, and the state survives a restart untouched.

## A new conversation comes back on the profile the process was launched with

`new_session` rebuilds pi's whole runtime — services, `models.json`, the catalogue — and
builds the new session's model from the **command line** pi was started with (`--provider`
and `--model`), not from the model the running session holds. A switch by `set_model`
belongs to the session that made it, so the next new conversation lands on the
launch-time profile. Measured on the emulator against pi 1.5.0, on two profiles of one
relay: picked B at 17:43:52 (`get_state` → `pikit-custom-relayb`), started a new
conversation, and the first reply of the new session, at 17:44:02.453, named
`pikit-custom-relaya` again.

Silent is the word that matters. The chip names a **model id**, and two profiles of one
relay commonly serve the same ids — a `deepseek-flash` on A and a `deepseek-flash` on B
draw the same chip — so nothing on screen says the provider moved. What follows is not
cosmetic either: the launch-time profile is one the reader was on earlier, possibly one
whose key has since been rotated away, and the first message of the new conversation is
then answered `401 … 无效的令牌` by the relay. That reads as a bad key, and the way out the
reader finds is tapping the model again, which is a `set_model` back onto the profile they
thought they were on — which is why the report was "only after tapping the model again
does it recover".

`PiAgentSession.stateActiveModel` closes it. After a `new_session` that was not
cancelled, the app reads the new session's state (`applyState`, the awaited half of
`refreshState`) and, when the model pi opened on is not the one the app is on, states its
own — the same `set_model` the picker sends, with the same two details: the provider id is
`launchProviderId`, because `set_model` matches on `m.provider === command.provider`; and
the thinking level is stated again afterwards, because pi answers a switch with the
model's own remembered level. A refused call falls back to a relaunch, which reads the
same store and so cannot land on the wrong profile either. The state read is *first and
awaited* for a reason worth recording: the first version compared against the state
`newSession` had just cleared and refreshed in the background, so it raced its own
`get_state`, decided on `null`, and stated the model on every new conversation — measured
in logcat as `new session opened on null/null`.

`modelToState` is the pure half: the pair the app wants against the pair pi answered,
null when they already agree — so a new conversation on the profile it was launched with
costs one round trip and no switch — and `SessionModelTest` pins the four cases, including
the same model id under another provider, which is the invisible one.

The alternative was to make every profile switch relaunch the agent, the way the app
already does when a profile's `models.json` entry is missing. Rejected for the reason the
picker's own switch is in place: a relaunch is a process teardown, a fresh handshake and a
re-read of the whole transcript for a change pi accepts over RPC. Restoring an old
conversation is the case this does **not** cover, deliberately: that session's model is a
fact about the transcript, not about the profile the app is set to, and the app has no
model of its own to state over it.

## The model catalogue is pi's, and stale is the default

pi resolves a model id its catalogue does not contain from a **copy of the provider's
default model** (`buildFallbackModel` in `core/model-resolver.js`): the copy keeps the
default model's `thinkingLevelMap`, context window, `maxTokens`, cost and `input`, and
pi says so on stderr — `Model "…" not found for provider "…". Using custom model id.`

That single mechanism produced three separate symptoms, and each one measured something
that does not look like a catalogue problem from the outside:

| symptom | what pi was actually doing |
| --- | --- |
| `deepseek-flash` shows **context 128K, max-out 16.4K** | the app had written a `models` definition that *replaced* pi's entry, so the window was the app's invented default |
| deepseek has **four** thinking levels, the app offered **three** | the fallback is `deepseek-v4-pro`, whose map is `{minimal, low, medium: null, high, max}` — three — where pi.dev's catalogue gives four |
| an OpenAI model has **six**, the app offered **five** | the fallback is `gpt-5.5` (five levels), and the model in question is not in the bundled snapshot |

Reproduced against the bundled runtime on the desktop bundle, with a fresh agent
directory and one dummy key:

```
$ node cli.js --mode rpc --approve --provider deepseek --model deepseek-flash
Warning: Model "deepseek-flash" not found for provider "deepseek". Using custom model id.
{"command":"get_available_thinking_levels","data":{"levels":["off","high","max"]}}   # 3
```

The catalogue pi consults is `$HOME/.pi/agent/models-store.json`, and **nothing pi
does on the RPC path writes it**: `refreshModelCatalogs` is imported by
`interactive-mode.js` and the model selector, and by nothing else. RPC mode *does*
start a fire-and-forget `modelRuntime.refresh()` at launch (`main()`:
`!offlineMode && appMode === "rpc"`), but that goes through `Models.refresh`, not
through the CLI's `refreshModelCatalogs`, and it only republishes the overlay
**inside the running process**; the store on disk is untouched. So an RPC-mode agent
reads whatever is in that store and never writes a newer one, however online it is,
and its knowledge is whatever the app last refreshed — on a fresh install, the
snapshot bundled with the release (`generatedAt: 2026-09-05`, against pi.dev's
catalogues of `2026-09-15`).

**PiKit runs pi's own refresh** — `pi update --models`
(`package-manager-cli.js`, `refreshModelCatalogs`: `ModelRuntime.refresh` with
`allowNetwork: true, force: true`) — and the same probe afterwards, with no change to
the agent's argv:

```
$ node cli.js update --models
Model catalogs refreshed
$ node cli.js --mode rpc --approve --provider deepseek --model deepseek-flash
{"command":"get_available_thinking_levels","data":{"levels":["off","low","high","max"]}}  # 4
```

Six properties of that command decide how the app uses it:

- **It visits configured providers only**, and "configured" means a credential
  *resolves* (`Models.refresh` skips a provider whose `resolveRefreshCredential`
  answers nothing). Measured with one key: 0.67 s, exit 0, one `models-store.json`
  entry carrying pi.dev's own `lastModified`; with no credentials at all it finishes
  in 0.25 s having written nothing.
- **The app gives it a credential for every built-in provider**, through
  `PiLaunchOptions.extraEnv` (`catalogueRefreshEnvironment`), because the model the
  user cannot select is usually in a provider they are not currently on. The value
  plays no part in downloading a catalogue — pi.dev's per-provider catalogue is
  public, and the credential only decides *whether* pi asks — so a placeholder is
  enough. Measured across all of them: ~757 KB over one concurrent request per
  provider, roughly one round trip. The real key is written over the placeholder for the
  provider it names, and the map never reaches the *agent*: pi builds the
  available-model list from the same "configured" test, so an agent launched with
  thirty-four placeholders would report every model of every provider as available and
  offer accounts the user does not have (`PiProcessLauncherTest`).
- **This is also what makes the store worth reading.** pi.dev serves a catalogue for
  every provider pi's own key table knows — measured directly: fourteen of them
  answer `200` with a model list, `minimax`, `xiaomi`, `kimi-coding`, `opencode`,
  `zai-coding-cn` and `ant-ling` among them, at byte counts matching the bundled
  `providers/data/*.json` — so a store holding one or two providers was only ever a
  refresh that had one provider's credentials. Widened, it becomes pi.dev's *complete*
  catalogue on disk, and the model page's "does pi know this id" question is answered
  from the file with no process at all (ARCHITECTURE §6.2).
- **The key goes through the environment, never argv.** `update` is parsed by the
  *package* CLI, which rejects an option it does not know, so `--api-key` here would
  fail the command outright — and a key in argv is readable through `/proc` anyway.
- **`force: true` steps over pi's own four-hour window**, so the app rate-limits it
  itself: `CATALOGUE_REFRESH_WINDOW_MS` is pi's own
  `REMOTE_CATALOG_REFRESH_INTERVAL_MS` (four hours), a failure buys half an hour of
  quiet (`CATALOGUE_RETRY_MS`), and the maintenance page's button is the manual
  override. Zero was the policy while the refresh covered one provider and is not one
  now that it covers thirty-four: ~757 KB per launch is not a launch-path cost on a
  phone.
- **It runs after the handshake, in the background, and nothing waits on it.** When
  the store actually changed, the running agent is holding the old catalogue — pi
  reads it at startup — so it is relaunched, and only while the agent is idle: a turn
  in flight is worth more than a correct level list, and the fresh catalogue is on
  disk for the next launch either way.
- **"Actually changed" is a comparison of the catalogue, not of the file.** The store's
  file is rewritten by *every* refresh, including the one with nothing to report: on a
  `304 Not Modified`, `remote-catalog-provider.js` persists `{ ...stored, checkedAt }`
  and `FileModelsStore.write` writes the whole document without comparing it to what is
  there. Comparing the file's `(mtime, length)` therefore reported a change on every
  run, and while `CATALOGUE_REFRESH_WINDOW_MS` was zero the "relaunch it" branch fed
  itself: agent start → refresh → file mtime moves → restart → agent start. The report
  is the chat header flickering between "starting" and "ready" for as long as the app
  is open. `catalogueRevision` projects out the two fields the agent never reads
  (`checkedAt`, pi's four-hour window; `etag`, its revalidation validator) and compares
  each provider's `models` and `lastModified` — what `remoteModels` consults when it
  decides whether the stored overlay beats the built-in catalogue. A restart is then
  never followed by another one, because the second refresh finds the same catalogue it
  just wrote. `CatalogueRevisionTest` pins the rule, and the window is what keeps it
  from being a loop even when no restart is scheduled.

If pi.dev's catalogue does not have the id either, the fallback **is** pi's answer,
and the app showing it is correct rather than stale. This app cannot know more about
a model than pi does.

## The level shown is pi's id, and the level saved is the user's

The app persisted **pi's answer**: `reconcileThinkingLevel` wrote whatever `get_state`
or `thinking_level_changed` reported back into `PiSettings.thinkingLevel`. The level is
a *preference across models* — one setting, every model the user switches between —
while pi's answer is about the one model that happens to be loaded, and pi clamps it.
So a model that clamps rewrote the user's choice permanently, and the worst case is
not subtle: `getSupportedThinkingLevels` answers `["off"]` for a model with no
reasoning support, so using one such model **once** wrote `off` into the preference,
and every launch afterwards passed `--thinking off` — for reasoning models too.

What replaced it is a remembered *list*: `PiSettings.availableThinkingLevels` holds
the last levels pi reported — **with the model id they were reported for**
(`availableThinkingLevelsFor`), because the list is a property of one model's
`thinkingLevelMap`: `deepseek-v4-pro` has three levels and `deepseek-flash` has four,
and remembering the levels without the model is how a picker comes to show the previous
model's menu for the second between a switch and pi's answer. `thinkingLevelsFor(live,
remembered)` gives the chip something to clamp against during that second, and a list
whose key is not the model in use reads as no memory at all. The preference itself is
never written by pi's answer. Two smaller things went with it:

- **The names are pi's ids, not translations of them.** The chip used to read `中`
  where `pi --list-models` and `--thinking` say `medium`; the level's *name* is the
  value that is sent, in every language, and only the sentence explaining it is
  translated. `Strings.Chat.thinkingLevelDescription` is that sentence;
  `thinkingLevelOptions` labels every option with the id — the composer's menu
  rows read it.
- **A model that does not reason gets one row, not a choice.** pi's answer for such a
  model is exactly `["off"]`, and a level list of one is a menu of one row — the id,
  its sentence, ticked — where a slider would have drawn a one-tick track that does
  nothing. That case was one of the things the slider version existed for, and the
  menu arrives at the same answer by being a list.

The picker's list is pi's, so a level this build has never heard of is offered when a
newer pi reports it, and `set_thinking_level` forwards it: the app is not the
authority on which levels exist, and pi clamps what it does not know. The command
builder's `require` used to throw for exactly that case — an error banner on a level
pi had just reported as available.

## The level shown is the reader's, mapped onto the model in use

The chip read pi's **live** level (`get_state.thinkingLevel`) before the saved one, on
the argument that pi is the authority on what is running. That is true of a process and
false of a *row*: the value pi reports after a switch is a level that belongs to the
model the reader came *from*, mapped by the model they arrived at. Measured against the
pinned 1.4.0, with `max` chosen on a model whose map is `{off, low, high, max}`:

| step | pi's answer | what the reader chose |
| --- | --- | --- |
| the four-level model | `max` | `max` |
| switch to a model whose map is `{off, high}` | `high` (clamped) | `max` |
| switch back to the four-level model | **`high`** — `max` did not come back | `max` |

So a chip that reads pi shows `high` where the reader asked for `max`, and the reason is
not a stale frame: the level pi carries is the *clamped* one, and information is lost at
every hop through a narrower model, in one direction only. The reverse case is the same
defect from the other end — a `max` that was chosen elsewhere arriving as this model's
`high`.

So the saved value is the input and `clampThinkingLevel` is the whole rule: your level,
mapped onto the model in front of you. `max` on a four-level model shows `max`; the same
`max` on the two-level Xiaomi model shows `high`; a model that can only do `off` shows
`off` while it is on screen. Nothing is written back, which is deliberate — persisting
the mapped value is what made one non-reasoning model's `off` permanent, the bug the
remembered *lists* above replaced.

The running process is brought to the same answer from the other side:
`PiAgentSession.selectProfile` sends this clamped level over `set_thinking_level` after a
successful `set_model`, reading the model's levels out of the catalogue on disk
(`levelsKnownFor`) because that is the only source that answers for a model pi is
*not* currently on. The chip and the process therefore agree without either of them
reading the other's echo, and a model the file does not describe — a relay whose own
`models.json` entry carries the map — leaves pi's own clamp of the carried level in
place.

### pi has a second opinion, and it is per model

Two separate mechanisms on pi's side can answer a level question before the app is asked,
and they were measured separately:

- **`set_model` carries the running level and clamps it.** Measured over RPC against the
  pinned 1.4.0: `off/low/high/max` with `max` chosen, a switch to a model whose map is
  `{off, high}`, and a switch back answers `high` — the level the reader chose is gone
  from the running process and does not return, because the value carried is the one the
  *previous* model clamped it to.
- **`settings.json` carries `modelThinkingLevels`, keyed `"provider/modelId"`, and it
  outranks `--thinking` when pi resolves the launch model**
  (`modelThinkingLevel: perModel ?? defaultThinkingLevel`, schema:
  *"Per-model default thinking level overrides keyed by `provider/modelId`"*). So a level
  recorded for a model in an earlier session comes back on every launch of it, whatever
  the app passed. That memory is written by the **interactive TUI**
  (`onModelThinkingLevelChange` → `setModelThinkingLevel`); the RPC path does not write it
  — measured: a whole probe run (two `set_model`, one `set_thinking_level`) left no
  `settings.json` behind at all.

Both are answered the same way, which is why `stateThinkingLevel` is called on **both**
paths: after `set_model`, and after the launch handshake (`--thinking` is not enough
there — the memory wins). `thinkingLevelToState` decides whether anything has to be said,
and `ThinkingLevelTest` pins both answers.
