# 9.3. The web-access page

*[Architecture](../ARCHITECTURE.md) §9.3.*

The bundled `pikit-web` extension and the one page that configures it. The
page's furniture — the app bar, the card, the row, the note — is §9.2's.

## One extension, two tools, one page

`pikit-web` is PiKit's own extension: one TypeScript file with no dependencies.
It registers exactly two tools, named the way dsh names its web tools:

- `web_search` takes one or more queries and returns an optional answer plus
  citeable sources. A multi-query call merges the results round-robin by rank
  and deduplicates by URL, so one tool call can cover several angles without
  asking the model to concatenate them itself.
- `web_fetch` takes one URL, fetches it, and returns readable text with the final
  URL and HTTP status. HTML is cleaned of script, style, hidden and embed
  elements before it becomes text; the result says it is external, untrusted
  content.

The settings page is one `PiPage`, not the old three-layer stack. Its shape
follows dsh's web-search page: a **Search** section with the provider menu and
the result cap, a **Fetch** section with its own provider menu and size cap, a
**Network** section with the two request timeouts, and one reset section.
The selected provider's own fields appear directly under the menu that selected
it — an API key, an endpoint, a Cloudflare account id, a model name — so the
question "what does this service need?" is answered where the choice is made.
There is no second "advanced" page and no free-form editor of the whole file.

One section is not the extension's: **New chat conversations** decides the
network-tools switch a new chat conversation starts with — Search on, Search off
(the shipped answer) or Follow the last. It lives here because this page is where
the reader decides what web access the agent has, and a new chat's answer to that
is the same question one step earlier. Its value is
`PiSettings.chatWebAccessDefault`, not `web.json`: `pikit-web` never reads it, and
`PiAgentSession` applies it when it builds a chat launch (§17).

## The provider table is the page

`WebSearchStore.WEB_PROVIDERS` is the single table the page is built from, and
`tools/pikit-web.ts`'s `PROVIDERS` is its mirror in the extension. Each row says
which fields a service needs and whether it can search, fetch or both. The page
draws a provider's fields from that row, so a service the extension supports
cannot be missing from the page, and a field the page draws is a field the
extension actually reads.

The services are the ones this project set out to support: DeepSeek, Z.ai, Exa
(and its keyless free endpoint), DuckDuckGo, Tavily, Ollama, Brave, Jina, OpenAI,
Gemini, Kimi, xAI, SearXNG, Cloudflare and SearchAPI. The table lists their
product names untranslated and their requirements in the interface's language.

**Automatic search** is the default and needs no key: it tries Exa Free first,
then DuckDuckGo, then the first configured keyed provider. A fresh install can
therefore search before the reader visits this page. A provider pinned by id is
used as-is; if its key or endpoint is missing the tool says which one, rather
than falling back to a different service behind the reader's back.

**Fetch is a separate choice.** `Automatic` and `Direct HTTP` are the same
keyless fetcher: no cookies, no inherited credentials, a size cap and a timeout.
Jina, DeepSeek, Ollama, Tavily and Exa can be selected when a page needs a
reader service; their keys are shared with the search section because a provider
is one entry in `providers`.

## The file, and why there is no editor

The extension reads `$HOME/.pikit/web.json`; `PIKIT_WEB_CONFIG` carries the
absolute path to the child, and a `pi` typed in the terminal falls back to the
same `$HOME` location. The document is small and strict JSON:

```json
{
  "version": 1,
  "enabled": true,
  "search": { "provider": "auto", "maxResults": 8, "timeoutSeconds": 30 },
  "fetch":  { "provider": "auto", "maxChars": 20000, "timeoutSeconds": 30 },
  "providers": { "brave": { "apiKey": "..." } }
}
```

`WebSearchStore` is its only writer. The page never mirrors it into
`SharedPreferences`: two copies of one setting are two answers to "which provider
is in use", and the agent reads the file the page did not write. A file that does
not parse is not overwritten at startup — the page shows one note and offers the
explicit **Restore defaults**, which is also the way out of a file edited into a
shape this build cannot read. There is deliberately no text editor of the whole
document: the extension has seven settings, and asking a reader to type JSON on
a phone keyboard was the old design's central mistake.

## What was removed, and why

The extension this replaces was a vendored npm package: about a hundred source
files, 30 MB of tree, forty-odd provider modules and a configuration file with
around 150 keys. The page had grown three layers — seven owned controls, an
"add an option or key" list of the other documented keys, and a text editor for
a file that could not parse — because the page was trying to present the
extension's own whole configuration surface rather than the handful of choices a
reader makes.

That surface is gone with the package. What replaced it is one provider table,
seven settings and two tools. The old extension's four tools (`web_search`,
`fetch_content`, `source_check`, `get_search_content`) and its four commands are
gone; chat mode lends a conversation `web_search` and `web_fetch` and nothing
else. The old `web-search.json` in pi's directory is left untouched as inert user
data but is no longer read, written or backed up.
