# What the model writes: Markdown

*[Architecture](../ARCHITECTURE.md) §12.1.*

What a reply is made of, and the walk that turns it into text. A formula is typeset by the
renderer in [§12.2](12.2-mathematics.md), and the tables, display formulas and marks are
[§12.3](12.3-display-and-marks.md).

The transcript's **Markdown** renderer is hand-written, and deliberately: a reply's vocabulary is
narrow — prose, fenced code, headings, lists, quotes, tables, inline emphasis — and those blocks
are cheap to draw directly, where a full CommonMark engine would be a dependency for constructs
the agent does not emit. `Markdown.kt` parses the blocks and the inline runs; `MathView.kt`
renders mathematics and owns the measurement of a formula, and the boundary of what each supports
is written out construct by construct in the source.

## What the parser handles, and what it does not

Blocks: fenced code (```` ``` ```` and `~~~`), ATX and setext headings, bullet, ordered and task
lists with nesting, block quotes holding further blocks, thematic breaks, pipe tables with
alignment, display formulas, and paragraphs with soft and hard breaks. Inline: escapes, code
spans, emphasis and strong emphasis, strikethrough, inline links and images, reference links,
autolinks, bare urls, and inline mathematics.

Deliberately absent, and each for its own reason rather than for lack of time:

- **Indented code blocks.** Four leading spaces are how a model indents a *nested* list, which is
  far more common in agent output; treating the indent as code turned a nested list into a grey box
  of its own source.
- **Raw HTML.** It is drawn as the text it is; silently swallowing a `<div>` would hide that
  nothing here renders HTML.
- **List items holding blocks.** An item is a string with a `depth`, so an item cannot hold a code
  block or a table. Recursing would make `depth` a property of the parser rather than of the item.
- **Footnotes.** The definition line is removed and no footnote list is drawn; the `[^1]` marker
  is left as text. A reply cites a paper rather than footnoting it, and every marker seen in
  practice pointed at something this app cannot fetch.
- **HTML entities.** `&amp;` is drawn as written. Decoding them is trivial and *not* decoding them
  is what makes a reply about HTML entities legible.

**Reference links are resolved at parse time, not at draw time.** `[label]: url` is lifted out of
the stream, and every `[label]`, `[label][]` and `[label][id]` below it is rewritten to
`[label](url)` before any block is drawn. Carrying the definition map into the token walk instead
would thread a map through `renderInline`, `rememberMathInline` and every caller of both for a
construct resolved once. A reference with no definition is left as written: `[1]` in prose about a
list is a `[1]`.

## Syntax highlighting, which was hand-written and has been removed

A code block was coloured by `SyntaxHighlight.kt`: one forward pass with no regular expressions and
no backtracking, in ten hand-written rule sets (shell, Python, Kotlin, Java, JavaScript, JSON,
YAML, SQL, Go, Rust), with a palette derived from the Material3 colour scheme the interface used
then. It worked, and it was removed.

**A code block was monospace and uncoloured** before it, and it is again. The libraries that do
this well are the wrong shape: Shiki and TextMate need a JavaScript engine and a grammar per
language, the Compose options are unpublished or a JS bridge, and `codehighlight-parser` (130 KB,
no network) needs Kotlin 2.3.20 where this project's compiler reads 2.1.0. The choice was never
"hand-written or a good library"; it was "hand-written, or not at all".

What settled the removal is the ten-rule-set ceiling: ten languages out of the hundreds a model
writes a fence for, with the feature absent exactly where the language is unfamiliar and present
exactly where the code was legible anyway — a keyword is an identifier matched whole,
and an unknown language is drawn plainly rather than guessed at. A file, a test, a palette and a
per-language list buys less than a wrong colour that cannot be told from a right one. What replaced
it is the fence's own language label, monospace at `bodySmall` — it says *what* the block is.

The old scanner's two properties still hold for anything that runs on every streamed token: it
cannot hang and cannot throw (a `"` with no closer and a `/*` with no `*/` are the *normal* state of
the input), and it is linear and yields offsets rather than styled text, so it has no opinion about
the theme and can be asserted on the JVM — the rules `tokenizeInline` in `Markdown.kt` follows.

## What the inline walk has to get right

The inline grammar and the mathematics are found by **one** tokeniser (`tokenizeInline`) and drawn
by **one** pass (`renderInline`). It used to be two walks: the paragraph was cut at its formulas
first, and the emphasis parser ran over the pieces — so `**b $x$ c**` reached the parser as `**b `
and ` c**`, neither half holds a pair of delimiters, CommonMark does not open an emphasis without
one, and both halves were drawn literally. The emphasis run is now open across the placeholder, and
for `**b $x$ c**` the assertion is that there is exactly one bold span, starting at `b` and ending
after `c`, with the formula as inline content inside it.

Three rules in the walk are load-bearing:

- **What is a formula.** `$…$` needs a closing `$` on the same line, no space just inside either
  delimiter, and a non-empty body — without those rules a price, "it costs $5 and $10 today",
  becomes the formula `5 and `. `$` is also escaped by a backslash, and the escape is counted
  rather than assumed: `$\pi$` must not be read as an escaped delimiter just because a backslash
  follows the opening `$`. `MarkdownMathTest` pins both. Deliberately *not* mathematics is a bare
  command — `\frac{1}{2}` on its own is text, because treating any backslash-command as mathematics
  turns `C:\Users` into a formula. A padded body is mathematics when it looks like mathematics: a
  `\command`, a script, a group, a relation, **or a row break** (`\\`) — the last one because
  `$ a \\[6pt] b $` carries no other markup, and without it the body stayed prose and `[6pt]` was
  parsed as a Markdown link (the report "换行间距指令如[6pt]不会正常渲染").
- **A refused formula falls back to its own source.** `inlineContent` returns null for an empty or
  unmeasurable formula, and appending a placeholder the map does not hold throws inside `Text`
  rather than drawing nothing; the walk puts the source text back. That path is also what a caller
  that is only *measuring* uses, which is why the two cases cannot drift apart.
- **The placeholder's alternative text is the formula's own source, on one line.** `TextMeasurer`
  measures a placeholder from its `Placeholder`, and the annotated string carries the size in an
  annotation whose tag is `androidx.compose.foundation.text.inlineContent`. A table column's width
  is measured through that pair (`MathInline.placeholders`), which is what makes a column holding a
  fraction as wide as the fraction rather than as wide as the source text beside it. Every newline
  in that alternative text is flattened to a space: `appendInlineContent` tags one *run of
  characters*, and Compose's inline content cannot span a line break — a multi-line body put its
  newlines inside the range and the placeholder never drew, which is half of the report
  "多行公式不显示". The renderer is still handed the body with its line breaks.

## The cost that is paid on every token

- **A paragraph's inline render is O(its own length), and used to be O(n²).** The old walk called
  itself on `text.substring(index)` for each piece between formulas, which copies the remainder of
  the message once per formula *and* once per formula-shaped `$` — a reply with a price in it, `$5`
  and `$10`, paid the scan twice per line. The walk is index-based now and the tokeniser is a single
  forward pass, so the cost is a function of the text rather than of the text and its dollar signs.
- **A block's `MathInline` is `@Immutable`, and that is load-bearing.** Compose infers a class's
  stability from its fields, and `AnnotatedString` and `Map` are both read as unstable; without the
  annotation every `Text` in a rendered reply was recomposed on every pass of the transcript —
  while an answer streams, every token, for every block on screen.
- **A reply is a plain `Column`, and the virtualisation moved into the formula.** A `LazyColumn`
  was tried for one round, on the reasoning above: the transcript's own list then measures *every*
  block of a reply to learn the height of the one item the reply occupies, and a formula's
  measurement is the expensive one. Measured with `FrameMetrics` on the emulator, that cut the
  layout pass from 305.9 ms to 218.4 ms.

  It is a `Column` again because the `LazyColumn` was a crash in two of the three places
  `MarkdownText` is drawn — the transcript, and `ManualPage`'s body, which is a
  `Column(verticalScroll)` like every settings page. A scrollable measured inside a scrollable gets
  `Constraints.Infinity` on the main axis, and a `LazyColumn` refuses it outright —
  `IllegalStateException: Vertically scrollable component was measured with an infinity maximum
  height constraints, which is disallowed` — which is the crash that opening the manual from Settings
  produced. A tall reply drew faster and a page could not be opened at all.

  What replaced the saving for one round was a per-block deferral (`DeferredMeasurement`); **it was
  measured and removed** — 763 ms against 741 ms on the 300-block reply below, because the
  placeholder is measured too and the parent still has to know the item's height. What paid is one
  measurer per reply rather than one per block.

**Why the `LazyColumn` looked safe.** "A nested vertical `LazyColumn` is legal" is true under the
transcript and false under a `verticalScroll`, and the rule was checked against the one caller that
satisfies it. A shared composable's constraints are the union of its call sites.

**The prompt bubble's width, got wrong the same way.** It lives in `ChatScreen.kt`'s `UserBubble`,
and Material3's `Surface` wraps its content in a `Box(propagateMinConstraints = true)`, so a cap
applied to the box *around* the bubble travels into the bubble's `Column` and stretches it — the
fixed-width bubble and the left-shifted user message are one bug, the text sitting at the start of an
86%-wide bar. The cap has to be imposed where `Surface` cannot see it, as a `widthIn(max = …)` on a
`BoxWithConstraints`; `Alignment.End` was never wrong, being `BiasAlignment.Horizontal(1f)`, i.e.
`space - size`.

## Inline code is real text, with the fill drawn behind it

`SpanStyle.background` is a plain colour fill with no corner radius, and ui-text 1.10 has no
`BackgroundStyle` — checked in the artefact. The first answer to that was to make a code span
*measured content*, like a formula: `rememberCodeChip` measured the span's text, wrapped the result
in a `Box` with a background and a 6dp radius, and declared it as an `InlineTextContent`. That
bought the radius and cost three things a reader notices, all of them measured on the emulator:

- **The selection could not highlight it.** A selection is drawn from the `TextLayoutResult` of the
  text it crosses, and that pass happens *before* inline content is drawn, so an opaque chip covered
  the highlight under it.
- **It could not be selected in part.** A placeholder occupies one character — `U+FFFC` — so a drag
  inside a code span took all of it or none, and copying a message that contained one put `U+FFFC`
  on the clipboard instead of the code.
- **It could not be padded.** The chip's box *was* the placeholder and the fill was drawn inside it,
  so the 3dp pad appeared outside the fill: `ripgrep` measured [277,430][436,488] with the fill
  stopping at the glyph advances, which is the "空余太小，戛然而止" a reader sees first.

The span is ordinary text in the monospace face now, tagged with a string annotation, and the fill
is drawn *behind* the whole `Text` by `CodeChipText` (`CodeChip.kt`). Everything a reader does —
selecting half of it, dragging the handles, copying — is the platform's own behaviour on real
characters, because there is nothing special about them any more, and the fill is the one part that
is ours. Verified on the emulator against a restored conversation: a long-press on the middle of
`` `pi --list-models` `` selected `models`, and the highlight drew over the chip.

Two numbers in the fill are the whole geometry, and both are the font's rather than the line's. Its
vertical extent is the style's own ascent and descent, measured on `"Hg"` with `lineHeight` dropped
— the same measurement `MathView` makes for a formula's baseline — plus 1dp; **filling the line
box is what made two consecutive lines of code look joined**, and the measurement that settled it
was on the type scale the interface had before Miuix: the chip was 58 px inside a 58 px line (that
scale's `bodyMedium`, a 22sp line box, at density 2.625), i.e. it touched the line above and the
line below. Its horizontal extent is the span's own advances plus 3dp, drawn outwards from the
glyphs because the layout no longer holds a wider box for it — the few dp it claims from a
neighbouring character are covered by that character's own ink rather than by a gap.

One rectangle is drawn **per line** the span crosses, so a code span long enough to wrap is two
chips, the same shape a selection of it takes. The table path is unchanged and remains the plain
`SpanStyle`: a filled chip in every cell of a measured grid reads as a grid of errors, and only the
widths are wanted there.

## The drawing layer is Miuix's

Everything in this file that *draws* comes from `top.yukonga.miuix.kmp` now, and the parser did not
move: `parseMarkdown`, the block model, the single token walk (`tokenizeInline` / `renderInline`),
`InlineStyle`, `MathInline`, the placeholder annotation and `clipEntryFor` are the same code. So is
`MarkdownText`'s contract — a plain `Column` inside a `BoxWithConstraints`, never a lazy or a
scrollable container, for the two kinds of call site above.

- **Text** is Miuix's `Text`, in both overloads: the `AnnotatedString` one carries a formula's
  `inlineContent` and hands the code fill its `onTextLayout`.
- **Prose** is `MiuixTheme.textStyles.paragraph` — 17sp, the size Miuix sets body text at — with
  the **line box raised to 26sp at the call site**. That is a consequence of the fill above rather
  than a preference: `paragraph` carries `1.2em`, which is barely above a Latin font's own box
  (about `1.17em`), so a chip drawn from the font's box outwards with 1dp of pad would touch the
  line above it — the defect *Inline code is real text* is about, coming back. The line box lives
  at the call site because it is a property of a block of agent prose, not of the application's
  type scale: a settings row at 26sp would be a different mistake.
- **Headings** are `title2` / `title3` / `title4` — 24, 20 and 18sp — which is Miuix's own ladder.
  The library carries hierarchy by *size* and its titles are normal weight, so the Material3
  "emphasized" styles the three levels used to be have no counterpart here; the gap above a level-1
  or level-2 heading is still what makes a manual chapter read as a break.
- **The code well** is Miuix's `Card` — a 16dp squircle, the library's own card radius — filled
  with `secondaryContainer`, holding the fence's text in the monospace face on `body2` at
  `MONO_LINE_HEIGHT`, with the fence's label in `footnote2`. A `Card` also *clips* what it holds,
  which the hand-ordered `background(shape)` it replaced did not: a line scrolled to its end
  painted past the rounded corner.
- **The table frame** is Miuix's `Surface` — clip, border and fill in the one order that works, so
  the hand-ordered `clip(shape)` before `border(…)` is gone (see [§12.3](12.3-display-and-marks.md))
  — with the header and the cells in `subtitle` and `body2`, and the grid lines and the rule
  between blocks drawn as `HorizontalDivider`s in the scheme's `dividerLine`.

Three colours were decided rather than inherited:

- **The inset fill is `secondaryContainer`**, for the inline chip, the code well and the table
  header alike — the role Miuix's own text field draws its resting well in. The Material3
  `surfaceContainerHigh` this used to be cannot be used: in Miuix's dark scheme it is the same
  value as the card a reply sits on (`#242424`), so a chip so coloured is invisible there.
- **The muted ink is `onSurfaceVariantSummary`**, for a quote's prose, a list's markers, a checked
  item and a fence's label, and it is provided through Miuix's own `LocalContentColor`. Miuix's
  text styles carry no colour of their own, which is what lets a heading or a paragraph inside a
  quote pick the muted ink up without knowing it is inside one.
- **The display formula's scroll fade is `surfaceContainer`**, and that is exact rather than a
  compromise: Miuix gives it the same value as `background` (`#FFFFFF` light, `#242424` dark), so
  the fade — which hides the ink it fades out — matches the reply's card *and* the manual's page.
  The Material3 version of that line had to pick one and be slightly wrong on the other.

The copy glyph's confirmation is the same 1400 ms swap, drawn by Miuix's `IconButton` with
`painterResource(R.drawable.ic_copy)` and `ic_check`, and the crossfade between the two runs on the
library's own spring (`folmeSpring(damping = 1f, response = 0.2f)`) now that the app's motion scale
was Material3's `motionScheme` and left with it. The glyph's 28dp box, its 18dp ink and the
`CopyButtonInkInset` the meta row aligns to are [§12.3](12.3-display-and-marks.md)'s.

## The tests that could not catch it

`Regex("^\\\\begin\\{(\\w+\\*?)}")` is accepted by the JVM and rejected by Android's own ICU
engine, which fails the whole class initialiser: every Markdown block in the app threw
`ExceptionInInitializerError` the moment a reply started arriving, and the JVM suite for the same
code was green. It is `indexOf` now. For a *rendering* change the unit tests settle the parser and
the device settles the renderer; the two do not overlap, so a third-party formula renderer has to be
verified on a device.
