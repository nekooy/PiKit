# 9.1. Pages, and which moves are one

*[Architecture](../ARCHITECTURE.md) §9.1.*

There is no navigation library. A second-level page is local state — a `sealed
interface` of destinations in Settings, a `Boolean` for the conversation drawer, a
`File` for the directory the files page is showing. The root's own move is one
`AnimatedContent`: the incoming page fades in over 220 ms while it travels a tenth of the
width from the side it belongs to — the chat from the leading edge, every pushed page from
the trailing one — and the outgoing page fades out underneath it over 140 ms. The direction
is chosen from `targetState`, because `AnimatedContent`'s `targetState` has already moved on
to the *next* destination by the time a second tap lands mid-slide.

The root's three pushed pages are the other case: the terminal, the files and the settings
each take the chat's place, so a tap on the capsules is a change of page with no direction
to be wrong about beyond the tenth of the width above. The capsules themselves are §13's:
the chat is the app's only root, and the pages it opens carry their own back arrow.

Three moves were missing one, and the audit that found them is the list of screens whose
*whole content* is replaced by a tap:

- **The conversation drawer.** It used to replace the conversation between two frames,
  then slid in as a full-width second level. It is neither now: it is a panel pulled over
  the conversation, and its motion is the drag's own number rather than an animation with
  a duration — see §13's *Navigation* for why that is what a drawer is.
- **A directory in the files page.** Entering a folder used to swap the listing instantly;
  it is this page's second level, and the way out is the header's own action row. Only the
  *listing* travels here, not the page's furniture: the location bar and the toolbar stay
  put, and what changes is the title, the trail and the count. That split is also why the
  read of the directory lives in the listing rather than in the page — a single read keyed
  on the page's state would be replaced the instant the move started, and both halves of
  the slide would then draw the new folder.
- **The terminal's session list**, which was a `DropdownMenu`. It is not a page any
  more: the switcher is a floating menu at its toolbar button (§7.1), which is the
  kind of move that replaces nothing.

Not pages, and deliberately so: the root's three destinations (the tenth-of-the-width
slide above, not a full page move), every sheet
(movement from the bottom edge, not from the side), every floating menu (a fade at the
thing it is about, §7.1), and every dialog (the platform's own
animation). The `ChatTab` → `ChatScreen` split exists so the conversation is read below the
window's chrome: a streaming answer changes that state several times a second, and a read in
`RootContent` would re-run the insets, the sheet layer and the page frame for every token.
The `key(session)` inside `ChatTab` makes a conversation switch a rebuild of the page rather
than a mix of two transcripts, while the composer — the draft, the attachments and the
transcript's scroll position — is hoisted above it per conversation (`ChatComposerState`), so
a look at the terminal does not cost any of them. Rows inside a page are not pages either: an
expanded tool card, an opened reasoning block and a switched terminal session all change
content *within* the page they are on, and an animation on those would be motion without a
move.

## A page's body has an elastic end, even when it fits

A page whose content fits the window used to be a page that did not move at all: a directory
with three files swallowed the drag that a directory with thirty answered with the give every
other scroll surface has. Nothing in the page was wrong — the gate is in Compose. `Scrollable`
reaches its overscroll effect only through `ScrollingLogic.getShouldDispatchOverscroll`, which
reads

    canScrollForward || canScrollBackward || overscrollEffect.isInProgress

and a viewport with nothing to scroll to reports the first two as false while nothing is in
progress at the moment a drag begins. `applyToScroll` is never called, the scroller consumes
zero, and the drag arrives at the node above it unattended. The fix is therefore not a flag on
the scroller but a nested-scroll connection *above* it: it is handed everything the scroller
could not consume — for a short page, the whole drag — and translates the content by a damped
distance that springs back when the finger lifts. That is the library's `overScrollVertical`, and
the app asks for it through one wrapper, `Modifier.piOverScroll()` (`ui/kit/PiOverScroll.kt`), so a
page that rolls its own cannot drift from the others' feel.

**Which containers get it.** The ones that *are* a page: the settings root and every settings
sub-page, the conversation drawer, the files listing, the manual's document column (the
contents row above it is the page's furniture, not its body), the model pages, backup,
maintenance, search, personalization and About — and a sheet body that stands in for the page the
content would otherwise be read on, which today is the file preview's text and the agent page's
context notes and instructions editor.

**The conversation and the drawer move as a pull, not as a transition.** The pair
used to be an `AnimatedContent`: a tap on the clock icon slid the list in over the
conversation. It is now a two-page stack with one number behind both — how far the
conversation has been pushed aside, 0 to 1 — because the list is also reached by a drag, and
a transition has no notion of following a finger. **The pull is rightward**: the conversation
slides off to the trailing edge and the panel is uncovered from the leading one, which is
what the reference screens show and what the reader means by "右滑打开历史". The first
version had the layers the other way round — a panel sliding over a dimmed page — and one
frame is enough to tell them apart: in one the conversation is pushed aside, in the other it
is covered.

**The commit rule is the platform's, and three rounds of home-made ones were not.** A release
completes when the drag passed **half the width**, or when it was a **fling faster than
`ViewConfiguration.minimumFlingVelocity`** in the direction of travel and had covered at least
5% of the width; otherwise the page settles at whichever of the two is nearer. The velocity is
a real `VelocityTracker` fed the pointer's positions, which is the component the platform's
own scroll and paging gestures use. What it replaced: a third of the width with a "last frame
is the velocity" heuristic, then a quarter with 2.5% — both guesses at the two numbers the
platform already defines, and both wrong in the same direction, because a quick thumb covers
about a fifth of a 1080px screen and every distance threshold above that reads as a gesture
that has to be *completed* rather than thrown.

**A tracker with too few samples reports zero, so the average is the fallback.** A
`VelocityTracker` fits a line through the samples it was given, and a gesture that arrives as
three events leaves it nothing to fit — measured on the emulator as `samples=3 v=0.0` for a
329px drag over 500ms, which is a fling that silently never happens. When the fit returns
zero, `distance ÷ elapsed` is used instead: the same quantity in the same unit, exact for a
constant-speed gesture, and never zero for a gesture that moved. With it, a 300px flick in
150ms opens, a 100px drag in 800ms does not, and a 600px drag in 800ms opens. Measured on the device: 150px in 60ms opens,
100px in 800ms does not, 600px in 800ms opens.

`AnchoredDraggable` — the library component this would be — was tried first and did not
receive the gesture at all in this layout: a state created with two anchors at 0 and updated
after the width was measured never dragged, and neither did a state recreated on the width.
The pointer events reach the page (a probe logged them), so the page-level gesture is a plain
horizontal detector with the platform rule above, which is the same policy without the
component that would not take it.

**The way back is the same gesture backwards.** Once the list has arrived, the conversation is
off to the leading edge and its own detector only sees drags that start on a screen it no
longer covers, so the list carries its own detector: a rightward pull closes it, with the same
rule read backwards. It is on the list's container rather than on its rows, so a vertical drag
still scrolls the list and only a horizontal one is taken.

The list is composed on the first open and then **kept**, parked off the leading edge at
progress zero: it scans the session directory, and dropping it on close made a quick re-open
a blank panel while it scanned again — measured: swipe out, swipe back in within a second,
and the rows arrived after the panel did. The number behind both pages is not `remember`ed
inside the chat page either: a conversation opened from the list rebuilds that page
(`key(session)`), and the close the tap started has to keep moving after the rebuild. It
lives in `ConversationDrawerState`, above the key, and the settle animation runs on the
root's scope — see §13's *Navigation* for the two defects that measurement fixed. Both
pages move with graphics-layer translations; the conversation's *touch* surface is a
separate transparent target over it, because a layer moves what is drawn and not what is
touched, and the conversation would otherwise swallow taps over the list it had left.

**One colour behind both, and only the card a step away from it.** The conversation is a
card while the list is out — it shrinks by 5% about its centre — so a strip of the window
shows above, below and at its trailing edge, and that strip has to be the panel's colour or
the seam is drawn twice: once down the panel's edge, and once as a black notch at each
corner of the card. It was the scaffold's `surface` (black in the dark scheme) beside a
`background` panel (#242424), which is exactly the seam the reader saw. The drawer's stage
box paints `background` itself now, so the panel and every strip the card does not cover
are one field, and the conversation is the only surface a step away from it. The light
scheme gets the same arrangement from white and #F7F7F7.

**Which do not, and why.** A region *inside* a page keeps no elastic edge of its own. A list
bounded inside a card — the picker sheet's options, the workspace folder picker in its sheet —
translates its content out from under the card's own rounded clip, so the corners would scroll
away with it; that is the same reason those two put their scroll modifier on the column inside
the card rather than on the card. A dialog body is a question in a frame rather than a
page, and a bounce inside that frame reads as a control that broke. A `MarkdownText` is not a
scroll container at all — a plain `Column`, by §12.1's hard rule — so a Markdown body has no edge
to give: the container it is drawn in carries the effect when that container is a page body. A
`LazyRow` is horizontal, which this modifier does not answer.

**Order in the chain is part of the rule.** On a `LazyColumn` the modifier goes on the list's own
`modifier`, and the list's internal scrollable is below it. On a
`Column(Modifier.verticalScroll(…))` — which is every settings page — it must come *before* the
`verticalScroll`: the connection finds its scrollers by walking ancestors, and
`DelegatableNode.visitAncestors` starts at `node.parent`, so a node placed after the scroller in
the same chain is downstream of it and receives nothing at all. Written after, the page still
compiles, still scrolls, and has silently lost the fix.

## Back belongs to the thing on top, and the gesture walks up a browser

Two back-gesture bugs came from the same place: nothing had decided what back *means* on a
page that is a browser or on a page with a sheet over it.

- **The Files page had no handler at all**, so back from three directories down finished
  the activity. Back on a listing means the listing above it, so the gesture now mirrors
  the header's parent arrow exactly — same enabled condition, same destination. Both walk
  **to the filesystem's root**, not to `$HOME`: the walk was gated at the home directory on
  the argument that the page is a view of the agent's home and its parent is the app's
  private data, but the listing shows `~/.pi` and the workspace, and a page that displays a
  directory's contents while refusing to display the directory above it is hiding its own
  subject. The Home button and the `~` crumb are the way back to the page's root, and above
  `$HOME` the trail is drawn as the absolute path from `/` — one crumb per level, so the
  location bar stays a way back rather than a single unscrollable segment.
  **The arrow is a drawn one** (`ic_arrow_up.xml`, Lucide's 2-of-24 stroke, 22dp of box for
  14 units of ink): it was the library's `ArrowRight` turned through a right angle, and
  rotated up that glyph reads as a *send* control — a filled head on a short shaft is the
  figure a phone's share sheet puts on sharing, not the figure a file manager puts on "the
  folder above".
- **A sheet lost the gesture to the page underneath it.** The modal layer registers its own
  `BackHandler` at the root, and pages are composed *inside* a transition: `Crossfade` and
  `AnimatedContent` subcompose their content during the layout pass, so a page's handler
  reaches the dispatcher **after** the layer's, and the dispatcher runs the most recently
  added enabled callback first. A page that was merely `enabled` therefore won, and a sheet
  stayed open while the page went back underneath it. Ordering the two
  handlers correctly would mean depending on the order two composition passes happen to run
  in. The Miuix rewrite removed the second handler from the page entirely: `PiPage` registers
  its `BackHandler` only when the page has a parent, and a Miuix dialog or sheet registers its
  own later in the composition — so the topmost thing always closes first, and no page has to
  ask whether a sheet is open.
- **The terminal view ate back and typed an escape instead.** `TerminalViewClient` declares
  `shouldBackButtonBeMappedToEscape`, and the page answered `true` — Termux's own default,
  where back is the hardware Escape a phone does not have. The focused terminal therefore
  consumed the key in `onKeyPreIme`/`onKeyDown`, wrote `\e` into the pty, and the page's
  `BackHandler` never ran. Measured on the emulator: two back presses on a fresh shell left
  the terminal on screen and printed `Display all 491 possibilities?` under the banner —
  readline binds `ESC ESC` to `complete`, and the prompt was empty. It answers `false` now,
  so the gesture leaves the page; the bar already has an `ESC` key and the page has a back
  arrow, which leaves back exactly one job. The app's own key panel is the thing on top
  while it is open, so it closes first (its handler is composed after `PiPage`'s), on the
  same rule as a sheet.

## The settings root flattened back out

The rows that state a fact — the environment, the agent process, About PiKit — were moved
behind an "Advanced" row to keep the settings root short, and that was one level too many:
opening the environment's paths or the agent's restart button cost a tap into a page whose
whole content was three rows, and the back arrow out of it landed on a page the user had
never seen. They are rows on the root again, with the two maintenance facts above them
stating their value in the value column. About PiKit is last and carries the app's own
version there, because it is the one row whose fact is about the app rather than about the
agent — and the fact a bug report is read against.

## The environment's page is rows of About PiKit

The environment had a page of its own, one row below the storage row, and it had nothing on
it to *do* — every row is a read-only fact — while repeating facts About PiKit already
carried: the bundled pi's version and entry point, the tool list and the agent's process
state were on both pages, and the process state was on the Agent page and the chat root's own
row as well. So the pages are one, and what was duplicated was **dropped rather than
merged**, because a fact drawn twice is a fact that can disagree with itself:

- **Kept from About PiKit:** the app's version, the package id, pi's version and its entry
  point inside `$PREFIX`, and the tool list — one row listing every tool, with the missing
  ones marked, rather than one row per tool next to a second row for `npm`.
- **Kept from the environment page:** the revision stamped into the unpacked image, and the
  three paths (`$PREFIX`, `$HOME`, the app's own files directory) with the note that a
  package installed under the prefix is relocated to it. Those paths are what a bug report is
  read against and had no other home.
- **Dropped:** the runtime's live state and the agent's process state. The root already gates
  the whole interface on the runtime being ready, and the Agent page is where the process is
  started, stopped and restarted.
- **Lost on purpose:** the `安装情况` section's second revision row (`运行环境状态`) was the
  same revision the installed-image row shows, read from the running status rather than from
  the stamp; and `npm`'s presence, which the updater reports by name when it fails.

Which card a row ended up in is a separate question from which page it came from, and the
split is by what a row belongs **to**: `应用` is the app and its own facts, `运行环境` is the
runtime the app carries. pi's version and the tool list are therefore in the second, directly
under the image revision — they live inside `$PREFIX` and arrive with that image, and under
the app's own version row the three read as one thing released together, which is the reading
[§3](03-what-is-baked-in.md) exists to prevent.

A saved page state of `Runtime` restores to the chat root, the way the retired `Advanced`
page does, so an upgrade cannot land the user on a page this build does not have.
