# Tables, display formulas, and the marks

*[Architecture](../ARCHITECTURE.md) §12.3.*

What arrives on screen once the parsing and the typesetting are done. The parser is
[§12.1](12.1-markdown-and-math.md) and the renderer is [§12.2](12.2-mathematics.md).

## Formulas in a table, which were not rendered

A table cell used to be rendered by a helper that flattened `$x$` to its literal source, so a
reply about a model's dimensions showed `$\frac{a}{b}$` where a fraction belongs. A cell is now
rendered by the same `renderInline` a paragraph uses, with the formula measurer attached, and the
*same* rendered cell is both what the column width is measured from and what is drawn — so the
measurement and the drawing cannot disagree about what the cell is.

The one cell-local decision is the code fill: a table measures its columns with
`InlineStyle(codeBackground = Color.Unspecified)`, because a filled span in every cell of a
measured grid reads as a grid of errors. The drawn cell keeps its fill.

## The known limit that is left

One limit is left, and it is not asserted by a test because it is not wrong, only absent: an
emphasis that wraps a formula *inside a table cell* is measured with the renderer detached (see
above), so a `/` in a cell is drawn as a literal. That is the same trade the column width makes.

**Tables.** `border(…, shape)` draws a rounded outline; it does not clip what is inside it, so
the header row's own rectangular fill painted *past* the rounded border — two square colour
blocks sticking out either side of the top corners. `clip(shape)` before the border is the whole
of that fix.

The width is a separate decision. The old layout gave every column a weight from a character
count, so a table with a handful of columns was squeezed until every cell wrapped and the rows
grew to ten lines. The columns are measured now, with a `TextMeasurer` on the cells' own annotated
strings, because the width of `缓存命中` and the width of `context` are not related to how many
characters they have. A column is capped at three fifths of the screen, and the table either fits
— filling the width with the cells wrapping — or keeps its natural width inside a horizontal
scroll. Three fifths is about the *scroll*: measured with a six-column table of sentences, 0.9
gave 1.1 columns per screen, a table read one column at a time with nothing on screen to say there
was a second, where 0.6 gives about 1.7.

## Selecting a formula, and the two shapes it made awkward

A display formula was inside a `horizontalScroll` box, and a `horizontalScroll` can claim a drag
that starts on its content. Since the transcript is one `SelectionContainer`, a formula written
inside a sentence could be selected and one written on a line of its own could not be dragged
across. Disabling the scroll (`userScrollEnabled = false`) then bought nothing: the
`horizontalScroll` claims only a *horizontal* drag, and the drag a selection uses is vertical. It
cost every over-wide formula its scroll, and the selection problem was solved properly instead, by
making the formula part of the text.

## Display formulas are paragraphs, and every consequence of that

A display formula used to be its own composable (`MathBlock`, a `Latex` in a `horizontalScroll`).
It is now a `Text` whose entire content is one inline content — the same mechanism an inline
formula uses — and four consequences follow from that one change:

- **It can be selected and copied.** A `SelectionContainer` selects what its `Text`s lay out; a
  composable beside the text is outside that, so a drag across a display formula selected nothing.
  The unselectable display formula is fixed by construction rather than by a gesture fix.
- **It is highlighted when selected.** A selection is drawn from the `TextLayoutResult` of the text
  it crosses, so a formula *inside* the text is highlighted by the same pass that highlights the
  words around it. An inline *code* span was the case that pass could not reach, because the fill
  it wore was a composable drawn over the highlight; making the span real text is
  [§12.1](12.1-markdown-and-math.md)'s subject. An inline formula is still a composable and is still
  highlighted, because its placeholder draws ink rather than a fill.
- **Long formulas scroll again.** `softWrap = false` (a wrapped formula is not the formula) plus
  `Modifier.horizontalScroll` on the parent — the scroll the section above wrongly disabled. A
  long-press still selects; a plain horizontal drag pans.
- **The delimiters have to be put back.** `MdBlock.Formula` holds the body with its
  `$$`/`\[`/`\begin{}` markers already stripped, and the inline path decides what is mathematics
  *by looking for a delimiter*. Handed the bare body it sees prose and draws the LaTeX source as
  literal text. `$…$` is the one pair that works, because `\[…\]` and an environment are blocks
  and re-fencing one inside a paragraph would make its body the paragraph's content.

## The command mark: six revisions, and the glyph that was chosen

The composer's command button is **Lucide's `command`** (ISC) — ⌘, one closed path with four
corner loops, drawn at the library's own stroke weight. It is not a `</>` at all, and that is the
point: the button opens a list of *commands*. Getting there took six revisions and three mistakes.
The first diagnosed `Icons.Filled.Code`'s blank button as `material-icons-extended` 1.7.x drawing
an open stroked polyline and Material3 zeroing the stroke; read out of the artefact that is false —
Material3 1.4.0's `Icon` calls `rememberVectorPainter(ImageVector, …)`, the overload with no stroke
arguments, and `Code` carries its own width of 4. The second was the real one: `ic_commands.xml` was
not in the APK at all, because an XML comment held a double hyphen, which XML forbids, and a
build-output filter hid AAPT's error — `unzip -l app-debug.apk | grep ic_commands` is the check that
settles it, on a *debug* APK, because a release one renames every resource to a two-character path.
The third was adjusting a glyph instead of choosing one: five
hand-tuned variants, all rejected because the figure no longer matched its neighbours. **An icon set
is a set**, and a glyph whose parts have each been individually adjusted no longer belongs to the
icons around it. What worked was twenty candidates from Tabler, Lucide, Bootstrap and Phosphor at
21dp, 55dp and 64dp — the 21dp column being the point. Tabler's `code` was chosen first and then
changed to Lucide's `command`, a single closed figure with no third stroke to crowd the other two
at 21dp. **For a glyph, render the real candidates at the real size and let
the person who will look at it every day decide.** A borrowed glyph's size is a call-site
decision: ⌘ at the 21dp the Material glyphs beside it use reads too heavy, because Lucide's
figure reaches 21 of its 24 units where Material's `Add` keeps its ink inside 14. It is **17dp**
in `ChatScreen.kt`, with the vector untouched.

Three hand-drawn `</>` candidates were rejected by arithmetic rather than by taste: the first two
overlapped a bracket by 2.2 and 0.3 units at 100 px/unit, and a later revision's self-intersecting
bracket path filled as a solid wedge — a 3.0-unit overlap that `tools/render-icon.py`'s row-by-row
mask comparison reported at the size the app draws. None of it would have failed the JVM suite,
which is why a glyph is chosen by rendering the real candidates at the real size rather than by
reading the path.

**The copy mark took four rounds, and three asked the wrong question.** Six *containers*, then six
glyphs from three sets, then five more sets; the answer was the SVG itself, pasted into the
conversation, and it is what ships: `ic_copy.xml`, two rounded sheets with the back one peeking at
the top right. Lucide's `check` (`ic_check.xml`) takes its place
for a moment after a tap, because its stroke weight is about the weight of the sheets' walls.
**When the question is how something should look, ask for a picture of the thing wanted** — every icon
set this project looked at draws that back sheet at the top *left* — and a sheet of six candidates
is six times the work of asking first.

**A glyph's path is data, and a rewrite of it is arithmetic.** `ic_copy.xml` is one `<path>` copied
verbatim, relative moves and all. The first version split it into two elements and turned the third
subpath's `m170.666666 -256` into an absolute move by hand — but a relative move is relative to
where the *previous* subpath ended (618.666667, 362.666667), not to where the first began, so the
back sheet was written 85.333 units too high and the two sheets sat 256 apart instead of 170.667.
Only the fill colour and `fillType` may differ; a character-for-character comparison of the two path
strings (771 characters) is the check.

**The copy button under a message was 5 dp in from the message's own edge, and it was the ink.**
The button is a 28 dp box with an 18 dp glyph centred in it, so the 5 dp nobody can see sits between
the box the row aligns and the mark itself; the row is pulled out by `(28 − 18) / 2` dp on whichever
side ends it — left for a left-aligned row, and right only when there is no timestamp there.
`CopyButtonInkInset` derives that from the button's own two sizes rather than writing the number
down twice. Measured with `uiautomator dump` at density 2.625, the glyph moved from x=46 to x=33
against the message text's x=32, and the timestamp kept its 18 px distance.

## One action, one colour

**The two copy buttons were not the same colour, and one call site was to blame.** Under a message
the meta row asked for `onSurfaceVariant` explicitly; the code block's header took `CopyButton`'s
default, `LocalContentColor.current` — whatever the bubble's `Surface` set, `onSurface` — near-black
in the light theme against the grey of the other. The default is now
`MaterialTheme.colorScheme.onSurfaceVariant`, named in `CopyButton` rather than inherited, and the
message call site passes no colour at all.

**The turn's furniture is the accent colour, and the code block's copy button is not.** The turn
summary row (`工作 X 秒 · N 个步骤`), a message's timestamp and the message's own copy button were
`onSurfaceVariant` and are `primary`; the code block's copy button stays `onSurfaceVariant`.
`MessageMeta`'s `color` parameter is gone with it, because both call sites passed the same value and
a parameter that can only hold one value is a place for two answers to appear.

The composer's controls are §7.1's ([§7.1](07.1-composer.md)); the rules these mistakes produced are in
`AGENTS.md`.

## A stale icon on the device is not a stale icon in the build

An old amber/gold icon was seen twice — in the launcher, then in the agent notification — after
every drawable had been changed to black and white. Both were the device's own icon cache, which
survives an APK update. Telling the two apart takes a minute and no device: sweep the built APK for
the colour's bytes (`6bc4ffff`, and both endiannesses of it, across `res/`, `resources.arsc` and the
compiled XML), where the current build reports none. A launcher or shade icon that is still wrong
after an install is cleared by a reboot or a reinstall, not by a rebuild.

The first-launch screen's own mark and progress bar are the launcher icon's white now
(`ic_pi_mark.xml`, `SETUP_FOREGROUND`) rather than the amber they were, and that one is settled by
reading the two drawables and the palette: no test can see a colour, and the icon checker covers the
launcher icon only.

## The thinking chip's jump, which was a lookup against the wrong key

The chip opened showing `medium` — a level the model does not have — and then settled on `high`.
The levels pi reported are remembered (`rememberedThinkingLevels`, keyed by
the model id) and the saved preference is clamped against them, but on the frame the app opens
`get_state` has not arrived, so `state.model` is null and
`saved.rememberedThinkingLevels(state.model?.id)` correctly refuses to answer; the list fell back
to pi's full seven levels, the saved `medium` was one of them, and the chip showed the raw
preference until `get_state` landed. The fix is one fallback: `state.model?.id ?: saved.modelId`,
because `PiSettings.modelId` is the model the agent was *launched with* and is the right key on
the first frame. The levels themselves are §7.2's ([§7.2](07.2-models-and-thinking.md)).

## The composer's tap handler, which swallowed every tap

Dismissing the paste/select toolbar that the field's own long-press raises is the one thing
`BasicTextField` cannot do for itself: it consumes a tap on its own bounds, because that is how it
moves the caret. The first version cleared the focus on **every** pointer event at
`PointerEventPass.Final`, which includes the down event of the tap that focuses the field — the
field took the focus, the handler cleared it in the same pass, and every later tap repeated it, so
no tap ever reached the field. It clears after a *completed* tap now, and only when the
field already had the focus when the finger went down (`awaitFirstDown(pass =
PointerEventPass.Initial)` reads the flag before the field's own gesture detector can change it).
The first tap focuses and stops; a second one dismisses. The composer is §7.1's
([§7.1](07.1-composer.md)).

## The commands list, which offered rows that could not act

The sheet was pi's own `get_commands` registry plus the app's own commands, on the theory that the
registry is an extension point and a hard-coded list goes stale. The theory was right and the rows
were wrong: everything the bundled `pi-web-access` extension registers — `/websearch`, `/curator`,
`/google-account`, `/search`, `/llama` — needs an interactive terminal, and several open a review
page in pi's own TUI and never answer over RPC at all. A row for one of those is a control that
cannot keep its promise. The list is now exactly what this page can run: the `!` shell prefix and
the seven commands in `BUILT_IN_COMMANDS`;
`commandDescription` and `PiAgentSession.availableCommands()` went with the rows rather than
staying as dead code. The sheet mechanism is §7.1's ([§7.1](07.1-composer.md)).
