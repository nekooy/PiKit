# 10.2. State and backup

*[Architecture](../ARCHITECTURE.md) §10.2.*

The other half of §10.1: what the app stores, where it lives, and which of it a
backup carries. The processes that own these files are §10.1's.

## Where state lives

| What | Where |
| --- | --- |
| Profiles, API keys, conversations, runtime | `<app files>/pikit-config.json`, `pi-sessions/*.jsonl` (written by pi), `usr` |
| Thinking level, default workspace, permission tier, language, text size, launcher icon, avatars, chat prompt template, agent mode, pins | SharedPreferences `pikit_settings`, `pikit_session_pins` |
| pi's own directory — the provider/model/settings files, the catalogue cache, the permission extension, any extension the reader installed | `<app files>/home/.pi/agent` |
| The mode each conversation was started in, and its web-access answer | SharedPreferences `pikit_session_modes`, one entry per session path plus `web:<path>` |
| The chat personas, their default, and which one a conversation speaks in | SharedPreferences `pikit_chat_presets` |
| The workspaces the reader added | SharedPreferences `pikit_workspaces`; the directories themselves under `$HOME` |
| Whether the first-launch storage prompt was answered | SharedPreferences `pikit_storage`; the grant itself is the platform's (`isExternalStorageManager`) |
| Whether the battery-optimisation exemption was asked for | SharedPreferences `pikit_power`; the exemption itself is the platform's (`isIgnoringBatteryOptimizations`) |
| The catalogue refresh deadline, and which conversation was open | SharedPreferences `pikit_model_catalogue` and `pikit_agent_session` — both re-decided on the next launch |
| Agent instructions and permission extension | `<app files>/home/.pi/agent/AGENTS.md`, `.../extensions/pikit-permissions.ts` |
| The permission tier in force | `<app files>/home/.pikit/permission.json` — a file, because the extension reads it per tool call (§14) |
| The rendered chat prompt | `<app files>/home/.pikit/chat-system-prompt.txt` — written for a chat launch from the template in `pikit_settings` |
| The built-in workspace | `<app files>/home/workspace` |
| Shared storage links | `<app files>/home/storage/shared` → `/storage/emulated/0`, one convenience link, while the grant holds (§5) |

Everything is under the app's private data directory, and uninstalling the app deletes all of it.
The app itself writes nothing outside it; the *agent* may, in a workspace on the phone and in the
tier the reader chose (§5, §14). The API key's exposure is in [§6.1](06.1-custom-endpoints.md).

**A workspace travels by its relative path, or not at all.** Every workspace under `$HOME`
travels as `workspaces/<its path relative to $HOME>/…`, beside the built-in one's
`workspace/` — an entry name a restore can decode back on an install that has never heard
of that folder, which is exactly the state a restore starts in. The added
list itself travels in the settings document (`pikit_workspaces`), so the menu is restored with
the files. A workspace *outside* `$HOME` — the picker can walk to `/sdcard/Dev`, and the tier
allows it — has no such relative name and is left out. That is a stated limit rather than a
silent half-restore: an absolute-path entry would let an archive write anywhere the app can
reach, which is the one thing the zip-slip guard in the format exists to prevent, and a
hand-picked archive must not be able to replace an arbitrary file on the phone. The list still
travels, so on the phone the folder came from it still has its files; on another phone the row
reappears and its files do not.

**A workspace that is `$HOME` itself travels under `home/…`, and the parts of `$HOME` another
entry owns are not packed twice.** `$HOME` is a legal workspace — the picker refuses only "that is
not a directory" — and its `$HOME`-relative name is the empty string, which
`workspaces/<relative path>` cannot spell. The tree loop used to drop it beside the folders
*outside* `$HOME`: the menu showed `~`, the export reported its entries, and nothing under it was in
the file. It has an entry of its own now, and that entry is deliberately narrower than a directory
copy: the built-in workspace, `$HOME/export`, pi's directory, the derived `.pikit`, the installer's
`.termux` and the `storage` links are carried by their own entries, and a folder that is also a
workspace in its own right keeps its `workspaces/…` name. The reason is not size, although `~` can
be large — it is that a second copy would be a *different* treatment of the same file. `MODELS`
redacts pi's JSON and withholds its derived names, so a plain workspace copy of `$HOME/.pi` would
have carried `models.json` verbatim with *Include API keys* off, and could have restored the
retired `pikit-permissions.ts`: the module pi loads on every tool call, and the one file (§14) says
must never come back from an archive. One rule now answers that for every entry that can reach into
pi's directory, and it is applied in both directions — the `workspaces/…` fallback a restore uses
for a folder this install has never heard of withholds the same names, so an archive cannot take
that road to install an older policy either.

**A file left directly in `$HOME` travels only when `$HOME` itself is a workspace.** `~/notes.md`,
a tool's dotfile at the root, is carried by the `home/…` entry above and by nothing else, because it
belongs to no project. Sweeping the whole tree by default was rejected: it would carry `.ssh`,
`.cache` and every other app's state into an archive that is offered as a file to hand to someone
else, and what the reader made as a *project* already travels by its own workspace.

## What a backup carries, and why a restore has to re-read

**Settings → Backup & restore** writes a selection of the table above to one `.zip` and puts it back.
The page is `ui/settings/BackupPage.kt`; the reasoning is here rather than in [§9.2](09.2-settings-pages.md)
because the subject is state ownership — which of these files is the app's, which is pi's, and which
of them anything actually reads — and not the layout of a page.

**The inventory below is the checklist, and a change that stores something new owes it a row.** A
new preference file, a new file under `$HOME` or `files/`, or a new store's directory is not finished
until its row is here and its entry is in `BackupArchive` in the same change. The failure this
prevents is the quiet one: the restore reports entries, the page says it worked, and one kind of
data simply never travelled.

| Data | Where | In the archive |
| --- | --- | --- |
| Basic settings — theme, language, text size, launcher icon, avatars' names and colours, default workspace, open-new-on-launch, chat prompt template, permission tier, agent mode, thinking levels, the retired flat `api_key` | `pikit_settings` | `SETTINGS`, as one typed document; `api_key` is dropped when *Include API keys* is off |
| The workspaces the reader added | `pikit_workspaces` | `SETTINGS`; the directories under `$HOME` travel as `workspaces/<relative path>/…` |
| The first-launch storage prompt was answered | `pikit_storage` | `SETTINGS` |
| The first-launch battery prompt was answered | `pikit_power` | `SETTINGS`; the exemption itself is the platform's (`isIgnoringBatteryOptimizations`) and cannot travel |
| The chat personas — the list, which one a new conversation starts with, and which preset each conversation speaks in | `pikit_chat_presets` | `SETTINGS`; the per-conversation selections travel in the same document, because a preference *file* is one entry |
| Model profiles, their keys, and which profile is active | `pikit-config.json` | `MODELS` |
| pi's own files — `models.json`, `settings.json`, `web-search.json` | `$HOME/.pi/agent` | `MODELS` |
| Everything else in pi's directory, including an extension the reader installed there | `$HOME/.pi/agent` | `MODELS`, as `pi/agent/…`; a new config file needs no entry |
| The composed `AGENTS.md`, pi's catalogue cache, and the two extension copies the runtime image installs | `$HOME/.pi/agent` | **no** — derived, re-downloaded, or re-installed; the permission extension especially must never come back from an old archive |
| The agent's instructions | `AGENTS.author.md`, `AGENTS.user.md` | `SETTINGS`; a restore recomposes `AGENTS.md` |
| Every saved conversation | `pi-sessions/*.jsonl` | `CONVERSATIONS`, with each file's own date |
| Which conversations are pinned | `pikit_session_pins` | `CONVERSATIONS` |
| Which launch mode each conversation was started in, and whether a chat conversation may use the web tools | `pikit_session_modes` — the mode under the session path, the web answer under `web:<path>` | `CONVERSATIONS`, whole file |
| Which conversation was open, and when the catalogue may refresh | `pikit_agent_session`, `pikit_model_catalogue` | **no** — where the reader happened to be, and a deadline the app re-decides itself |
| The avatar pictures — the two speakers' and each chat preset's | `files/avatars` | `SETTINGS`, whole directory |
| The built-in workspace, every added workspace under `$HOME`, and `$HOME` itself when it was added | `$HOME/workspace`, `$HOME/…` | `WORKSPACE`; `$HOME` itself travels as `home/…` (below) |
| A workspace outside `$HOME`, such as `/sdcard/Dev` | anywhere the picker reaches | **no** — its relative entry name is the archive's only safe form, and this one has none (below) |
| The HTML a reply's `/export` wrote | `$HOME/export` | `HTML_EXPORTS` |
| The permission tier in force | `$HOME/.pikit/permission.json` | **no** — a projection of `pikit_settings`, republished at the end of a restore |
| The rendered chat prompt | `$HOME/.pikit/chat-system-prompt.txt` | **no** — a projection of the template, rewritten by the next chat launch |
| The runtime, its stamps and logs, the package-repair ledger, the catalogue probe's scratch tree, the storage links, the shell banner, `files/dns-pins.txt` | `usr/`, `files/…`, `$HOME/…` | **no** — rebuilt from the APK, re-derived, or a fact about this phone's network |
| The copies of the pictures prompts were sent with | `files/chat-pictures` | **no** — derived from the conversations, which carry the bytes: a restore re-derives every copy the transcript asks for (§7.3) |
| The copies of the files a prompt was sent with | `files/attachments` | `CONVERSATIONS`, whole directory — a session names one by path and holds none of its bytes, so this is the only thing a restore could put back (§7.1) |

**pi's directory is carried as a tree, and that is the one structural lesson in the list.** Thearchive used to name four files under `$HOME/.pi/agent`; a reader who dropped their own extension
into `extensions/`, or a newer pi that reads one more config, lost it on a reinstall with nothing
anywhere saying so — a whitelist cannot notice a file it was never told about. So the directory
travels whole under `pi/agent/…` and only the *derived* names are withheld, in both directions: the
composed `AGENTS.md` (rebuilt from its halves), `models-store.json` (pi's cache, refreshed on a
four-hour window), and the two extension copies the image installs. Withholding
`extensions/pikit-permissions.ts` on the way back in is not tidiness: pi loads every module in that
directory, `installPermissionExtension` only runs on an install or a content update, and an archive
that restored an older policy would judge tool calls by it until the next update — and the retired
`pi-safety-guard.ts` would judge them by *two*, the stricter one winning, with no switch anywhere
that turns it off (§14). The four files this build knows keep their shorter entry names
(`pi/models.json`, …), so an archive written before the tree is still read by a build that has it,
and a build without the tree skips the extra entries instead of refusing the archive: the format
number stays 1 because the change is additive.

**Two rows of the state table above are absent from this one because they are not stored at all.**
The terminal's shells and the live conversation pool are process state: a shell's scrollback dies
with the shell, and a turn in flight is not a file — there is nothing for a restore to put back, and
a backup that claimed to carry them would be promising something no file on the device holds.

**Two halves travel differently, and the difference is otherwise a silent one.** Files are copied byte
for byte and extracted back to where they came from. Preferences are *not*: a `SharedPreferences` file
is not the source of truth while the process runs — every value the app reads comes from an in-memory
copy loaded at the start of the process — so writing `shared_prefs/pikit_settings.xml` behind the
app's back would change nothing until the next launch. The preference files therefore travel as one
typed JSON document each (`BackupArchive.encodePreferences`) and are applied through the API on the
way back in. Each value is written as `{"type": …, "value": …}` rather than as a bare JSON value,
because the type is not recoverable from the value: `1` is a valid `int` and a valid `long`, and
`getInt` on a `putLong` throws — into whoever reads it next, not into the restore.

**The agent's instructions travel as the two halves, never as the file pi reads.** `AGENTS.md` is
*derived* — `AgentContext.compose` rebuilds it on every launch — so an archive that carried it would
restore a document with no halves, and the migration that splits a pre-split file would then read the
whole default text as the reader's own. `AGENTS.author.md` and `AGENTS.user.md` are two entries of the
`SETTINGS` category, and a restore recomposes `AGENTS.md` at the end of the import
rather than leaving the previous composition in place. Measured on the device: an archive taken with
`AGENTS.user.md` = `MARK-ONE`, a file changed to `MARK-TWO`, a restore — the half came back as
`MARK-ONE` and the composed document contained it once.

## The five switches, and the two groups they are read in

The inventory is the storage truth; the page is one reading of it, and it is framed as **five
categories in two groups**:

- **The app and the agent** — `SETTINGS` (the preferences *and* the two `AGENTS` halves), `MODELS`
  (the profiles with their keys, and pi's whole directory).
- **Your content** — `CONVERSATIONS` (the sessions, the pins and launch modes, the attachment
  copies), `WORKSPACE`, `HTML_EXPORTS`.

**The agent's instructions are no longer a category of their own.** As `AGENT_PROMPT` they were one
switch for two small files, and a reinstall that left it unticked restored an agent answering in a
voice the reader never chose: the instructions are part of "this install behaves like this install"
exactly as the theme is, and they are a few kilobytes. The id is a *stored* value, so
`BackupCategory.fromId` still resolves `agent-prompt` to `SETTINGS` through `LEGACY_IDS` — dropping
the name would have made an old archive restore without them and report success, which is the one
failure mode a restore report must never have.

**Six flat rows became two groups**, because their weights differ by four orders of magnitude — two
prompt documents between a profile file and a project tree — and a list a reader cannot price is a
list they either tick all of or none of. The group is a *reading* decision and is written nowhere in
an archive: `BackupPage`'s `CategoryGroup` only decides which `PiSection` a row is drawn under, so a
category can move between groups without touching a byte of anyone's backup. A group with no rows in
it is not drawn, which is what lets the restore review show an archive's own halves under the same
two headings the export list uses.

**The key switch is not one of the five.** `包含 API Key` used to be a seventh row among the
contents, where it read as something to pack; it is a property of the archive — the manifest carries
the answer, and an archive from someone else shows it beside the date — so it sits in a group of its
own beside the button it modifies.

**The default is `SETTINGS + MODELS + CONVERSATIONS`**: the three things a reinstall cannot get back
on its own, now including the agent's instructions. The page says so in one sentence under the
groups, because a tick list with two unticked rows and no reason reads as arbitrary — and the reason
is size, which the workspace and the exported pages can both be enormous at and nothing else can.

**Nothing under `usr/` is in the archive.** The runtime is hundreds of megabytes of image unpacked out
of the APK, so a reinstall puts it back — the same for `usr-staging/`, `runtime-revision.txt` and pi's
own `models-store.json` catalogue cache, which the launch path refreshes on a four-hour window
([§3](03-what-is-baked-in.md), [§6.2](06.2-models-and-catalogue.md)). The catalogue's *deadline* is in
`pikit_model_catalogue` and is deliberately not exported either: it is one timestamp this app
re-decides by itself, and a restored one would either do nothing or make the app skip a refresh it
should have made. The same test — *is this derived, or a fact about this install* — is what keeps
`$HOME/.pikit`, `$HOME/.termux/motd.sh`, the `$HOME/storage` links, the package-repair ledger under
`files/pkg-restore/`, the catalogue probe's scratch tree and `files/dns-pins.txt` out. The last one is
worth naming because it sounds like user data: it pins hostnames for the network the phone is on, and
a restore onto a phone on another network is the case it would be wrong for. The package ledger is
the other one that sounds like data and is not: it is the list `pkg install` added, and every entry
on it is a package apt can install again — what a restore onto another phone would need is not the
list but a working network and the reader's own memory of what they wanted. Nothing was made by the
reader there that they would have to make again, which is the test the archive's contents answer to.

**A file attached to a prompt is staging, and its copy travels with the conversations.** A picked
document is copied into the app's own `files/attachments` and the message names that absolute path;
the session file holds the path and **none of the bytes**, so a transcript restored without the
copies is a history whose every attachment points at nothing. The copies therefore ride in
`CONVERSATIONS` under `attachments/…`, which is the one category where "the conversation as it was"
is the whole promise. The page's subtitle says so, because a category that quietly carries up to
256 MB of documents has to name them. A conversation whose copies were never in the archive — an
older install, or a restore that chose other categories — still shows the path, so the message reads
as one whose attachment is no longer on this phone rather than as one that never had an attachment.
The *pictures* are the opposite case and stay out (their bytes are already inside the session), see
the row above; that the copies live under `files/` instead of the cache is §7.1's argument, and the
two are separate.

**Three derived things are rebuilt at the end of an import, not carried.** `AGENTS.md` is recomposed
from the restored halves (above); `$HOME/.pikit/permission.json` is republished from the restored
`permission_mode`, because the permission extension reads *that file* on every tool call and the
launch path only rewrites it when a launch follows — a restore that finds the agent stopped would
otherwise leave every `pi` typed in the terminal judged by the tier the archive replaced (§14); and
the `$HOME/storage` links are recreated **before** the workspace files move, because a workspace
reached through `~/storage/shared` exists only while its link does, and `mkdirs` on a dead link drops
the files without an error. The other projection, `$HOME/.pikit/chat-system-prompt.txt`, needs no
work at import time: nothing reads it until a chat launch writes it anew.

**A restore is a merge, and nothing is ever deleted.** An entry of the archive replaces the file of
that name; a preference is applied key by key, so a key the archive does not carry keeps the value it
has and every other file stays. "Restore" sounds like *wipe, then write*, and a design that did that
would delete the user's current workspace to make room for an older one — a tap that destroys a day's
work, with the file picker's own three taps as its whole warning.

**The agent is stopped for it.** pi holds the conversation it has open and rewrites `models.json` and
`settings.json` at the start of every launch, so a restore made under a running agent is undone by the
next thing the agent does — or lands in the middle of a turn it is still writing. The manager stops
it, applies, and starts it again on the restored configuration. The restart is in a `finally`, because
the one outcome worse than a restore that did not happen is an app whose agent has silently stopped.

**Writing the files is only half a restore, and the other half is a list.**
`PiAgentSession.reloadAfterRestore` is that list. Every store here read its file once, at construction,
and then holds a copy: `SharedPreferences` hands a single cached instance to everyone who asks,
`SettingsStore` publishes a `StateFlow` built from an `AtomicReference`, `WebSearchStore` holds the
document it parsed, and the conversation listing caches its parse keyed by `(path, modified, length)`.
A restore that wrote the files and left all of those alone would show a restored theme, language,
model and conversation exactly as they were before it — indistinguishable from a restore that did
nothing. It is one function rather than each store watching its own file because `SettingsStore` →
`ProfileStore` → the agent launcher is a single chain with one reader at its end, and a second watcher
would be a second answer to "who owns this file". It runs **before** the agent is restarted, because
the launch path re-derives `models.json` and `settings.json` *from* the restored profile — and it
re-derives those two files itself, on the same profile, because a restore that finds the agent
already stopped never reaches a launch. Without that half, the archive's own `settings.json` is all a
hand-run `pi` can read, and one taken before the defaults were first written leaves the terminal page
typing `pi` into a process with no model at all.

**The archive is refused before anything is written.** The manifest is the first entry of the zip, its
`format` is the one field an import refuses on, and what is selected is unpacked **in full** into a
staging directory before any of it is moved into place — so a truncated download, or a zip the
platform refuses halfway through, fails with the app untouched. A staged entry's target is measured
against the staging root's canonical path, the same zip-slip guard `BootstrapInstaller.safeTarget`
uses for the runtime image: an entry name is a string the archive chose, and `..` in one is an archive
that writes outside the app.

**The keys question is asked, and the answer travels.** `pikit-config.json`, `models.json`,
`settings.json` and `web-search.json` can hold credentials in cleartext, and
`android:allowBackup="false"` is in the manifest precisely to keep them out of cloud backups. The
page therefore carries one switch — include the keys or not — and the manifest records which was
chosen, because it cannot be worked out from the entries: a profile with its key blanked looks
exactly like a profile whose key was never filled in, and the reader of an archive somebody else
handed them has to be told which of the two they have. What comes out is **one recipe for every JSON
document the archive carries**, because all of them are hand-editable and the field names are not a
fixed list: a key named `apiKey`/`apiToken` or ending in `ApiKey`/`ApiToken` is blanked — the suffix
rule is the same one the extension's own options table implies, and a newer provider's field needs no
edit here. Two details are load-bearing. A value that starts with `$` is an *environment reference*,
not a secret — `models.json` names the variable that holds the key (`"$PIKIT_KEY_…"`, §6.1) — so it
is kept, and blanking it would produce a file the custom endpoint cannot resolve while protecting
nothing. And the walk descends into arrays as well as objects, because a profile is an element of
`profiles` and the extension's provider table is a list: an object-only walk missed the files the
recipe was written for. A file the redaction leaves unchanged is copied **byte for byte**, so a
document with no key in it keeps the reader's own formatting and comments; re-encoding is the price
of redaction and is paid only when something was actually taken out.

**The run is owned by the session, not by the page.** A workspace backup is thousands of files, and a
restore is a stop, an unpack and a restart; the page leaves the composition the moment the
user looks at another one. `BackupManager` therefore hangs off `PiAgentSession`, beside
`repairInstalledPackages`, which walks `$PREFIX` for the same reason — and not off the composition the
way `CatalogueUpdater` and `StorageSelfTest` are, because those run for seconds and their result is a
line of text, where losing this halfway is a half-restored device.

**The destination is the system's file picker, not a path.** The archive has to be able to leave the
app, and the app has no business choosing where it goes; `CreateDocument`/`OpenDocument` is also what
keeps the whole feature working with **no** storage permission at all.
