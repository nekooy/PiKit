# 10.1. Process ownership

*[Architecture](../ARCHITECTURE.md) §10.1.*

```
PiHost  (process-wide singleton — the app-wide half)
  ├─ TermuxEnv + BootstrapInstaller   first-run unpack, one per app
  ├─ SettingsStore                    provider / model / key / tier
  ├─ TerminalSessionManager           the terminal page's shells, and which one shows
  ├─ model catalogue + refresh window one models-store.json, one deadline
  └─ the pool: up to PiHost.MAX_ANSWERING answers in flight and MAX_LIVE
     children resident, and which conversation is active (§15)
PiAgentSession  (one per live conversation)
  ├─ PiProcessLauncher → Process      `node cli.js --mode rpc ...`
  ├─ PiRpcClient                      framing, correlation, stderr, shutdown
  ├─ ConversationReducer              events → ConversationState (pure)
  ├─ StateFlow<ConversationState>     observed by Compose
  └─ StateFlow<AgentStatus>           one process's lifecycle
PiAgentService  (foreground service)  keeps the children alive while an answer arrives
```

The split is §15's: a fact two conversations cannot disagree about — the image, a
setting, a shell, pi's catalogue — is the host's, and everything about one process is a
conversation's. `PiAgentSession` keeps its public shape and delegates the shared half, so
a screen that says `session.env` still means the one environment.

The reducer is a pure function over `(ConversationState, PiRecord)`, so the state machine is
testable on the JVM against captured wire traffic — no device, no live model. The service owns no
state, so the UI can bind and unbind freely and a turn keeps running when you leave the app.
What any of these processes store, where it lives, and which of it a backup carries is
§10.2.

**A launch belongs to the conversation, not to the page that asked for it.** The chat
page's own `rememberCoroutineScope` used to start the process when a conversation was
opened from the drawer or the composer's `+`; `startAgent` spends seconds preparing the
environment files and the handshake, and a quick swipe to another destination disposed
that scope first. Compose cancels the caller with `ForgottenCoroutineScopeException` —
"rememberCoroutineScope left the composition" — and the launch's catch-all turned that
`CancellationException` into `AgentStatus.Failed`, so the composer reported an agent
failure for a page that had simply been left. The launch now runs on the root's scope,
which outlives every destination, and `startAgent` treats cancellation as an abandoned
attempt: it closes anything it had already spawned and leaves the conversation `Stopped`
rather than raising a failure.

## The entry exists while an answer is being written, and not otherwise

A foreground service exists *because* of its notification: that is the deal Android offers. What
the app does control is *when* that entry is up, and the answer is now **only while at least one
conversation is streaming** — `PiHost.streamingConversations` is the count, and the entry is
dropped the moment the last answer settles ("应用在后台后的通知改为只有有 ai 在输出时才有"). A
persistent "agent is running" between turns said nothing the reader did not know, and the turn
that a reclaim would actually destroy is the one worth telling them about.

Two conditions, and both are required: something is streaming, and no window is in front. The
Activity is already keeping the process alive while the reader is looking at it, so the entry
there is noise over a turn they are watching. `MainActivity.onStart`/`onStop` tell the service
which side of that line the UI is on; the collectors keep the claim honest on the other axis (a
pool that empties, a conversation that is closed, a stop the user asked for).

Between turns the service keeps running without the foreground claim. That is a deliberate trade
and it has a cost: with no notification the service is a background service, and Android may
reclaim it — which loses the terminal's shells and costs a relaunch on the next prompt, but
cannot lose a turn, because a turn is exactly when the entry is up and the claim held.

When the entry *is* up it is silent: `PRIORITY_MIN`, an `IMPORTANCE_MIN` channel with no sound or
badge, one line of text naming how many conversations are answering, and a Stop action that stops
all of them. A user who wants even that gone turns the *Agent* channel off in system settings:
`startForeground` still succeeds and the service stays a foreground service.

Keep-alive has three layers, and the report "息屏后会直接 terminated" is what made the third one
necessary:

1. **The foreground service**, with `android:stopWithTask="false"` so a swipe-away does not take
   the child with it. The shade entry only appears while the UI is gone.
2. **Two wake locks.** A turn lock per conversation (`pikit:agent-turn`) is acquired on
   `agent_start` and released on `agent_settled` — it keeps the CPU awake *and* the child's
   stdout drained for the length of one turn, and a second conversation answering at the same
   time holds its own. The background lock (`pikit:agent-bg`) is held while the UI is gone and
   an answer is arriving, which is the window in which a suspended radio would truncate a
   stream.
3. **The battery-optimisation exemption.** Neither of the above survives a power manager that has
   already decided to reclaim the process. `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` is the system's
   own dialog and cannot be granted by the app; the Agent page's keep-alive row reports whether
   it is held and offers the ask.

Two lifecycle facts are load-bearing, and both were measured on a device rather than reasoned:

- **`startForeground` is owed before the agent is up, not when it is.** A cold launch is in
  `Stopped` while the runtime image unpacks, which is far longer than Android 12+'s five-second
  deadline. Waiting for `Running` before promoting is a
  `ForegroundServiceDidNotStartInTimeException` on first run. The service promotes as soon as it is
  started and the status collector takes the entry away again if the agent is not actually up — a
  brief "running" during `Starting` is the cheaper lie.
- **The service tracks `AgentStatus` rather than deciding once in `onStartCommand`.** Deciding once
  meant a start that later succeeded from the UI — the Agent page's Restart, `scheduleRestart`
  after a settings edit, the one automatic recovery after a crash — never brought the service back,
  so the turn that needed keep-alive most was the one running without it; and a deliberate stop from
  the Agent page left the shade claiming "running". The collector keeps the notification honest,
  tears the service down when a stop the user asked for lands (debounced, because the two restart
  helpers stop and start in one breath), and `startAgent` itself asks for the service on success,
  which is what covers every caller that is not `MainActivity`.

## The terminal's shells are the process's, and a close is not a choice

The terminal's sessions are process state for the same reason. A shell created inside
`TerminalScreen`'s composition dies with it, and the terminal page is one the reader leaves
by its back arrow, so a look at the conversation killed a `pkg upgrade` or a running build;
`TerminalSessionManager` holds them beside the agent and the page only displays one of them.

**A shell carries the directory it was started in.** The manager is the host's — a long build
must survive a conversation switch — but the directory is the conversation's: opening the
terminal from a workspace shows the shell already running there, and opening it from another
workspace opens that workspace's own shell instead of moving a running one. The reader reaches
for the terminal to inspect what the agent did, and a shell standing in `$HOME` makes every
relative path a question. This is also why the Files page opens in the same directory: both
pages are views of the workspace the conversation is working in, and `$HOME` — pi's
configuration and every session — is one step up rather than the page's root.

Which one it displays is a rule of its own, `TerminalSelection.afterClose` — a pure function
over the roster's ids, tested on the JVM, because a screenshot cannot tell the two answers
apart: the page shows one shell either way. The wrong answer showed up only in *which* one.
Closing a shell from the switcher moved the selection onto the shell that had taken the closed
row, so with three shells open, ending `Terminal 1` while reading `Terminal 3` left the page on
`Terminal 2`. A close now moves the page only when the closed shell was the one on screen, and
then to the session that took its row — the row the reader was looking at — else to the last
one, because there is nothing below the last row. Closing every shell (`closeAll`) is the same
invariant taken to the whole list: one replacement, selected, since every candidate is gone,
and it opens where the selected shell stood rather than in `$HOME`.

The roster is never emptied. A close that would leave none opens a replacement and selects it,
rather than being refused: the terminal is a page the reader opened on purpose, and the one
thing worse than a shell the reader did not ask for is a blank rectangle with nothing to type
into.

## The workspace is the conversation's, not the app's

The agent's working directory used to be one setting on the settings page, and one value for
the whole app. It is now a *workspace*: a directory, one of a list, chosen per conversation.

**Why the list.** One directory is one project, and a phone is used for several over a week.
With a single working directory the history read as one undifferentiated stream of
conversations from different folders, and going back to an old one meant retyping the path it
belonged to. `WorkspaceStore` holds the list — the built-in `$HOME/workspace`, which cannot be
removed, plus the folders the reader added — and `pikit_settings`'s `defaultWorkspace` says
which one a *new* conversation starts in. The composer's first chip picks the conversation's
own; the agent page's `默认工作区` row picks the default; the drawer groups by it.

**Why a relaunch rather than a `cd`.** The workspace is the child process's working directory
and the base every relative path in a tool call resolves against, and pi reads it once at
startup. So `PiAgentSession.selectWorkspace` remembers the directory, clears the remembered
session — the conversation on screen belongs to the directory being left — and restarts the
agent; `restoreRememberedSession` then opens a fresh session there instead of the old one. The
same machinery in the other direction is the conversation drawer: a saved conversation records
the directory pi was started in (`{"type":"session",…,"cwd":…}`, its **first** line), so tapping
a row from another workspace binds the conversation to that file and records the directory
(`PiHost.openConversation`); the transcript is read from the file, and the process the first
prompt starts is launched there and rebound to the same session
(`PiAgentSession.restoreAfterLaunch`). A pi standing in the wrong tree would show the old
transcript while every tool call acted somewhere else.

**The `cwd` is the grouping key, not a second table.** `SessionMetadata.read` takes it from
that header record, which means the drawer groups conversations from before this change
— and conversations a `pi` typed in the terminal wrote — without the app having to remember
anything of its own. `sessionGroups` (tested in `SessionGroupingTest`) names each group the way
the composer's chip names that folder, keeps the group holding the newest conversation first,
and puts a directory the list no longer offers into a group of its own rather than dropping
its conversations: a project the reader deleted is still a project whose conversations they may
want to read. Sessions whose file records no directory at all are one last group.

**A workspace that arrived from outside the app is adopted.** The `cwd` header is also how a
directory gets *into* the list without the picker: a reader who runs `pi` by hand in the terminal
— or any pi that starts in a directory of its own — writes a session whose first line names that
folder, and the drawer then grouped it under a workspace the composer's menu had never
heard of. The same conversation in two places disagreeing about where it lives. `listSessions`
now adopts every distinct `cwd` that still exists and is not already in the list, added exactly
the way the picker adds one so the order, the dedupe and the deleted-default fallback all behave
the same; a directory that has since been deleted is skipped, because it cannot be launched in.
The scan also runs once at launch, which is what makes the menu complete before the drawer
has ever been opened — and what makes the drawer's list ready on its first frame.
