# The terminal's key bar

*[Architecture](../ARCHITECTURE.md) §7.4.*

## The terminal's key bar: a scrolling row of keys and three actions

The bar is **one row of keys and three round buttons**, drawn on the terminal's own dark rather than
on the app's light palette — the page behind it is black, and a light strip along its bottom edge read
as a second surface rather than as part of the terminal.

The keys are `滚动` (the follow-the-output toggle), `↑`, `↓`, `←`, `→`, `ESC`. `滚动` leads because it
is a *state* and belongs where the thumb already is; the arrows are what a soft keyboard does badly;
`ESC` ends the row because a shell asks for it least. The three round buttons are **not** keys — they
act on the bar and on the input path rather than sending a byte: send-text, the app's own keyboard, and
the IME.

### The keys scroll, and each is as wide as its label

An earlier version divided the row into nine equal slots so every key always fit. It fitted, and it
was wrong: on a 360dp screen nine slots are 25dp each, which is a key a thumb misses, and the bar
exists to save typing — a key that cannot be hit is worse than one that is off screen. The row is a
`horizontalScroll` now, each key is sized by its label, and the three actions stay outside it because
an action that slid off the edge is a control the reader cannot find.

### The three round buttons

**Send text** opens a field and sends what is typed there to the terminal **exactly as typed**. It
used to append a carriage return, so the string was *run*; that was wrong for the case that matters —
a `git commit -m` message is written to be reviewed or completed, not executed the instant it is
pasted. Measured: `echo noenter` typed in the sheet lands on the prompt's line with the cursor after
it and no output line.

**The app's own keyboard** (the laptop button) raises a panel of keys above the bar: five rows from `Esc`
and the digits to `Alt`, the arrows and `Space`. It is not an IME — nothing inserts text into a field;
every tap is a byte sequence handed to the pty, so the terminal's own line editing, history and
`Ctrl+C` are what the reader is talking to. The three modifiers are **latches**: they stay down for one
key and then let go, which is what a desk keyboard does with a chord and what a phone cannot do with
two thumbs. `Ctrl` maps a letter to its control code, `Alt` prefixes the escape byte, `Shift`
uppercases or picks a digit's shifted symbol, and all three can be latched at once. Measured on the
device: `Ctrl` then `c` prints `^C` and a fresh prompt, `echo` + `Space` + `hi` + `↵` runs.

The panel is a rounded card and it is the bar's **sibling in the page's column**, not an
overlay: the terminal view is measured above it, so the panel pushes the shell's last lines up
instead of covering them. The bar's key row is a scroll container whose viewport carries the
same rounding, because a scroll container clips to its own rectangle — a half-scrolled key was
being cut by a straight vertical line inside the pill, which reads as a rendering fault rather
than as "there is more to the left".

While the panel is up the IME is put away and the terminal stops raising it on a tap
(`TerminalHolders.imeSuppressed`): two keyboards that both answer one tap would fight over one cursor.

**The keyboard** (`⌨`) raises or lowers the phone's IME on the spot. Both glyphs are Lucide borrows
(`ic_laptop.xml`, `ic_keyboard.xml`) because the Miuix set has neither a keyboard nor a
left-right arrow, and the size is the call site's decision as it is for every borrowed glyph (§12.3).

### What the two-row bar cost, and why the keys that went are gone

Two rows of ten keys each replaced a cross-shaped arrow pad on the argument that the rows were
a *reading rule* — the line being typed, then the session. The rule was right and the shape was
wrong: the reader who has to use the bar is holding a phone in one hand, and a second row puts
half the keys past the thumb's reach for a bar that exists to save taps. The keys that went
with it — `CTRL`, `ALT`, `TAB`, `PGUP`, `PGDN`, `HOME`, `END`, `C-D` and the five symbols —
are all reachable another way: `TAB` from the soft keyboard, the rest through the send-text
field or a typed command. What stayed is the eight that were pressed.

### What this replaced, and why the history matters

The bar was one horizontally scrolling row of chips, arrows first as a flat `← ↑ ↓ →`, then
a two-row grid in which the arrows were a **cross** (`↑` above `↓`, `←` and `→` flanking
them) on the argument that a flat arrow row is not a d-pad: the eye reads left to right and
has to stop and count to find "down". Uniform keys did the rest of the alignment — every
cell the same rectangle, so `↑` is above `↓` because both are the middle cell, and no label
can be clipped by a neighbour's width, which four earlier attempts at measuring columns each
got wrong in a different way.

Two things ended the cross. The first is a *picture*: the bar the reader wanted has the
arrows in one row, and a request for a shape outranks a reading argument. The second is that
the rows now have a rule of their own — with the arrows first in a row that is explicitly
"the line being typed", counting from `↑` to `↓` is not the task, because nothing to their
right is another arrow. What was kept is everything the cross was *made of*: one size for
every key, `ArrowPad`'s measurement (`rememberKeySize`), the `TextMeasurer` pass before the
first layout, and the rule that the width is the widest label's plus the chip's padding.

**The bar has been two rows for a long time, and the reason changed.** It was two keys tall
for the arrow cross's sake, so a single row of keys beside the cross left half the height
empty wherever that row did not reach — and the row reached past the right edge and scrolled
instead of using the space below it. The split then was `EXTRA_KEYS_PER_ROW`, six keys under
`CTRL` and `ALT`, chosen because six is where the two rows came out within one key of each
other. That was a *packing* rule and it said nothing about what a key was for; the two rows
are now the two paragraphs above, `CTRL` and `ALT` still latch and still lead their row, and
the count per row is whatever the rule puts there.

**The other frame went too, and the keys are one block.** The arrow pad and the keys beside it
were two `KeyGroup`s 16dp apart, each on its own `surfaceContainerHigh` track — so what the
reader saw was one strip with a seam down it, the same raised surface at two insets, which
reads as a rendering mistake rather than as two sets of keys. The two scrolling rows are in
one card now, and the two action buttons sit outside it: they are the bar's own controls
rather than keys, so they are the one thing on the bar that is *not* on the keys' track.

**Both of a key's dimensions follow its label, and one of them did not.** The width has
been measured from the text since the uniform-size rewrite; the height was a flat 34dp,
and the type's line box is scaled by the system font size — `labelLarge` was 20sp at 1.0,
36sp at 1.8 — so at a large text size every key in the bar clipped its own label top and
bottom. Measured on the emulator in Japanese at font scale 1.8: the chips drew 34dp tall
around a 36dp line box, `スクロール` was cut to `スク`, and the bar — whose height was a
constant 76dp derived from *30dp* chips, two revisions behind the 34dp ones — was 8dp
shorter than its own two rows, so the second row sat on the bar's bottom edge and was
drawn over by the tab strip. The height is now the larger of 24dp and the label's measured
line box plus its padding, and the bar's height is derived from that rather than written
down.

The 34dp floor was the composer's `ControlChip` height, adopted so the two tappable pill
families matched. At that size the keys read as oversized against the terminal's own
text: the bar is chrome around a dense monospace transcript, and a 34dp/50dp key is a
composer pill dropped into it. Two passes took them down: first the padding (11dp/7dp
around the label became 8dp/5dp, floor 28dp), then the type as well — `labelMedium`
instead of `labelLarge`, because the larger face's line box alone kept the chips near
28dp however tight the padding got. They are now 24dp tall with 6dp of horizontal and
4dp of vertical padding, about 36dp wide for the widest shipped label, and 8dp corners
rather than 10dp. The bar at font scale 1.0 is therefore about 62dp rather than the
34dp revision's 84dp; at 1.8 it still grows with the label, which is what keeps the
whole bar on screen.

The label had a bug of its own in English. The bar caps every key's width at
`MAX_KEY_WIDTH`, and `Line break` was 72dp of `labelMedium` monospace — longer than the
cap, so it drew clipped, which is the "terminal newline button text is broken in English"
report. `Newline` was the same fact inside 51dp, and shortening the label was the fix
rather than raising the cap, because the cap is what bounds how far the row scrolls.

That answer runs out where a label has no shorter form. `スクロール` is five full-width
glyphs — measured at 184px, 70dp, plus the chip's padding — so the Japanese bar against a
64dp ceiling drew `スク` and dropped the rest of the word. The ceiling is now 72dp (it was
96dp while the chip's padding was wider and the type larger), which is where the longest
label the bar ships ends, and it still does its job: the width every key is given is the
*widest* label's, so a language whose labels are short pays nothing for the ceiling being
higher. What changed for Japanese is that the row scrolls further — the arrow pad is the
first thing in it, so the arrows stay on screen at scroll offset zero, which is the cost
the ceiling was bounding. A label past the ceiling is now marked as truncated
(`TextOverflow.Ellipsis`) rather than cut mid-glyph, so the next translation that outgrows
it is visible rather than silently wrong.

The line-break key sent a bare `\n` on the theory that its job was the shell's `>`
continuation prompt. That theory was wrong twice: the newline character *is* the line
delimiter in a canonical-mode terminal, so the shell read the line and ran it — "the
newline key is a carriage return" — and the missing glyph case it was written for was
never what the key was for. It now sends `lnext` (`0x16`, the terminal's `^V`) followed
by `\n`, so the newline is quoted and lands *inside* the line being typed: readline
handles the `^V` as `quoted-insert` in non-canonical mode, and a program reading whole
lines has it done by the line discipline. `\r` from the soft keyboard still runs the
line; the key writes it.

The scroll toggle has been through three shapes: a wide two-line button pinned to the
right of the bar, showing its state in an icon *and* a word, which made the least-used
control the most prominent thing on the bar; an icon-only square, quieter but saying
nothing; and now the word `滚动` in a key-sized cell, so it reads as one of the bar's
keys because it is one. **Only its tint changes when tapped** — `primary` while
following, `error` while paused — so it keeps its size, its word and its shape and
cannot be misread as a mode it is not.

The toggle drives the vendored `TerminalEmulator.isAutoScrollDisabled()`, whose
`onScreenUpdated` already implements what follow-off should mean — a row shift is
subtracted from `mTopRow` instead of the view snapping to the bottom — so a long
command's output accumulates *below* the part being read and nothing jumps. It is the
only mutator the emulator exposes (`toggleAutoScrollDisabled`, no setter), so the flag
is read back and flipped only when it disagrees: calling the toggle unconditionally
inverts the state on every recomposition.

The bar's choice is UI state, not emulator state, and it is mirrored into the emulator
from the `AndroidView`'s `update` block rather than only from an effect: the emulator
lives in a `View` that Compose recreates on every tab switch, and the effect has nothing
to attach to at the moment the state is first set.
